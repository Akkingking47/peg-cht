### 提取口径与自证

- 对每个连续差异段，在 ±4 字节内枚举能覆盖它的 2/4 字节小端窗口，取「窗口起点=差异段起点、宽度最小、能打标签」者。
- 标签：`w / w-1 / w-4 / h / h-1 / h-28 / h-30`（绝对值，旧→新分辨率的定值）；`dx / dy`（平移：旧值 +224 / +168）。
  799/796/599/570/572 与 dx/dy **代数恒等**，保留绝对标签只为可读；唯一不等价的是 571 → h-28(=740)。
- 结果：**382 差异字节 = 259 个连续段 = 259 个站点 = 0 认不出 = 0 未覆盖**；
  `.text` 52 个（h 21 / w 20 / h-1 4 / w-1 4 / h-28 1 / h-30 1 / w-4 1），
  `.data` 207 个（dx 163 / w-1 22 / h-28 14 / h-1 6 / dy 2）。
- 自证：`python patch_resolution.py --repro --quiet` → 内存构建 259 站点改完、中文补丁三处仍在，
  落盘产物与 v4 产物 **md5 相同、逐字节一致 ✅**。

### 中文补丁必须保留的三处（脚本每次构建后复核）

| 项 | 定位 | 期望字节 |
| --- | --- | --- |
| charset | VA `0x4718E3`（.text）→ FO `0x070CE3` | `6a 86` |
| `__mbcodepage` | VA `0x4ABC8C`（**.data**）→ FO `0x0A948C` | `a8 03` |
| 日期 LCID | FO `0x07BE86` | `b8 04 08 00 00` |

> ⚠ 踩坑记录：VA→FO **必须走节表**。套 `.text` 的 `VA-0x401000+0x400` 公式在 `.data` 上会把
> `0x4ABC8C` 算到 `0xA948C` 之外的错误位置（本轮的第一次生成就踩了，已修）。

### 补丁脚本接口（生成物）

`--w / --h`（默认 1024×768）、`--out`、`--apply`、`--repro`、`--quiet`。
条数断言：母本 md5 必须等于 `c462e897b3aa1c384870c857ce9e01df`；站点逐个做内容断言；
全部改动先写内存 → 回读校验 → 才落盘（`out\*.exe`）；拒绝 `w<800 或 h<600`
（v4 的右移/下拉假设只在该区间成立）。`--w 1280 --h 960` 干跑通过，`--w 640 --h 480` 被拒。

## 三、S2：花屏根因定位

### 工具与产出

- `work\peg\probe_res_coverage.py`（只读，依赖 capstone 5.0.7）
  - 全 `.text` 线性反汇编（168982 条指令；capstone 遇坏字节会停，脚本跳过坏字节继续，并统计跳过数）
  - 用 `ins.encoding.imm_offset/imm_size` **精确定位立即数的内存地址**，才能与 v4 站点表（记的是立即数地址）严格对账
  - 四类普查：(A) 尺寸家族立即数 改了/没改；(B) 16bpp 行字节数(pitch)候选；(C) DirectDraw vtable 调用点及其上下文；(D) 关键全局引用点
- 产出：`work\peg\out\res_coverage_probe.txt`（全量明细）、`work\peg\out\res_missing_candidates.tsv`（未覆盖候选清单）

### 结论 1（根因，高置信）：视口裁剪仍在按 800×600 算

三处**近乎相同的滚动/视口裁剪助手**，每处都是「先 `cmp` 限值、再算可见尺寸、最后 `Blt` 呈现」：

```
0x44C724  cmp dword ptr [0x663388], 0x320   ← v4 改成了 1024
0x44C72E  jle 0x44c74a
0x44C730  mov eax, 0x320                    ← ★未改，仍是 800
0x44C735  sub eax, dword ptr [0x663380]     ; 800 - 滚动量
0x44C73B  mov dword ptr [0x4a2730], eax     ; 写进 Blt 矩形的右边界
0x44C740  mov dword ptr [0x663388], 0x320   ← v4 改成了 1024
...
0x44C792  push 0
0x44C794  push 0x1000000                    ; DDBLT_WAIT 指纹
0x44C799  push 0x663380                     ; RECT
0x44C79E  mov eax, dword ptr [0x676904]     ; 表面对象
          ... call [eax+0x14]               ; IDirectDrawSurface::Blt
```

- 「`cmp` 说 1024、算术用 800」**同一基本块内自相矛盾**，任何取值都不可能同时正确。
- 算术结果直接写进 Blt 矩形（`0x4a2728/2c/30/34` = left/top/right/bottom），
  即 **Blt 覆盖范围仍被钉在 800×600**（配合 `.rdata` 视口常量 `0x498D40`=w-1、`0x498D44`=h-28 已被 v4 改成 1023/740）。
- 因此右侧 224 px、下侧 168 px **从未被写入** → 显示未初始化表面内存：品红/绿横条 + 黑块。
  与旧分支截图（顶栏/底栏因 `.data` 矩形被拉伸而**正常**、右侧花屏）**完全吻合**。
- 同一缺陷共 6 处（三对）：
  `0x44C730`(800) `0x44C777`(600) / `0x44C869`(800) `0x44C8B0`(600) / `0x44CC67`(800) `0x44CCAE`(600)。

### 结论 2（系统性缺陷）：v4 只改了一半的「同一个常量」

- `.text` 里尺寸家族立即数共 **145** 处，v4 只覆盖 **52** 处；未覆盖 **93** 处
  （其中「尺寸型」写法 82 处、「位掩码」写法 11 处）。
- 82 处尺寸型候选里，**仍带旧分辨率值（800/799/796/600/599/572/571/570）的有 43 处**，按语义分组：

| 组 | 地址 | 说明 |
| --- | --- | --- |
| 视口裁剪运算 | `0x44C730 0x44C777 0x44C869 0x44C8B0 0x44CC67 0x44CCAE` | ★结论 1，6 处 |
| 运行期构造的矩形对 | `0x41C4D4`(571→740) `0x41C4DB`(799→1023)；`0x42E496`(599) `0x42E49B`(799)；`0x45A0F1`(571) `0x45A0F6`(799)；`0x45A94A`(571) `0x45A94F`(799)；`0x4700DA`(800) `0x4700E1`(600)；`0x46CF42`(800) `0x46CF4B`(600) | 视口/贴图矩形，10 处 |
| 屏幕边框 | `0x44C5CC`(570→738) `0x44C5D1`(796→1020) | v4 只改了 `.rdata` 里同值的常量，这两条 push 漏了 |
| 坐标夹取/边界 | `0x4567C2 0x4567DC 0x4568E0 0x4568FA 0x45696D 0x456982 0x456A3D` | cmp/mov 799/599，7 处 |
| 尺寸全局初始化 | `0x4421D4 0x4421DE 0x442219 0x442223` | 写 `[0x676968/6c/88/8c]` = 799/599，4 处 |
| 其它 | `0x46B2AA`(push 800)、`0x40E741`/`0x40E74C`(600)、`0x467297`/`0x46795C`(add 600)、`0x40187D`(sub esp,600) | 6 处，需逐个看语义 |

- 反向观感：母本里**本来就有**一批 1024/1020/768 家族的常量（`0x428A68 0x428AB4 0x428ABD 0x434936 0x43493F 0x434948 0x434951 0x434989 0x43AB72 0x43ABAD 0x43AD44 0x4423AF 0x442DAE 0x44596A 0x45BA34 0x45BA3D 0x45BA46 0x45BA4F 0x45C7E3 0x45D131 0x45D13A 0x45FEDB 0x45FEE4 0x45FEED` 等，形态多为 `mov word ptr [0x49xxxx], 0x400` / `push 0x400`，另有 5 处 `push 0x3fc`(1020)）。
  ⇒ 线索：引擎里可能存在**面向 1024 宽的内部缓冲/布局路径**（也与旧分支 `res_constants.txt` 记录过 1024×768 常量族一致）。是否可被「原生触发」值得单独探一次，但**不是**当前花屏的原因。

### 结论 3（否定旧假设）：stride/pitch 不是根因

旧分支最后 3 个探针（`probe_res30/31/32`）在追「按 800 像素行距读写 1024 宽缓冲」。静态证据否定该方向：

- `push 0x640`(1600) 出现在 `0x410DB2`，是 `memset(0x69d020, -1, 1600)` —— 一张 **4×400 字节的定长表**（同函数 `0x410D72` 用 `imul edx,edx,0x190`(400) 做行距写 0xffff），与屏幕行距无关。
- `push 0xc80`(3200) 在 `0x4426F7`，是 `memset(0x641620, 0, 3200)` = 400×8 的定长表。
- `add eax/edx, 0x4b0`(1200) 在 `0x4672D3`/`0x46799B`，是传给导入函数（`[0x6aa598]`/`[0x6aa628]`）的**参数偏移**，不是表面行距。
- 唯一真正的「硬编行距」是 **BMP 写盘函数** `0x4144A9`(Lock) … `0x4147BD`(Unlock)：
  `mov word [ebp-0x25c], 0x4d42`('BM')、头长 0x36、`BITMAPINFOHEADER` 0x28、
  宽 `0x320`、高 `0x258`、`biBitCount 0x18`(24bpp)，逐行 `imul edx,edx,0x320` 读源像素。
  ⇒ 这是**截图/存图功能**，改动它只影响导出的 BMP，不影响画面。副产物：它是天然的「导出画面取证」工具。

### S2 未解 / 待动态确认

- 三处裁剪助手在 800 宽时代的精确语义（`[0x663388]`/`[0x6769A8]` 到底是「剩余可用宽」还是「屏宽」）
  只能靠动态 trace 定论；静态可确定的是**同一块内不自洽**。
- `0x41C4D4/0x41C4DB` 与 `0x41C026`(Lock)/`0x41C10C`(ReleaseDC) 相邻，是「拿 799×571 矩形去 GetDC 画字」还是「读回尺寸」，需看调用者。
- v4 产物**从未有过视觉证据**：唯一截图 `shot-v3.png`（01:01:51）早于 v4 产物（01:12:02），
  所以「v4 右列已右移」目前**无画面证据**（代码上是 `COLUMN_RECS` 位移 +224，应成立）。
