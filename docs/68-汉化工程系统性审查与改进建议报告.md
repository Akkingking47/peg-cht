## 一、总体评价

**结论先行**：本工作区在**「唯源 + 可复算」的工程纪律上显著高于社区个人汉化项目的平均水平**（假汉字黑名单、补丁三纪律、层表门禁、临时重建→回读→落盘等做法，多数社区项目并不具备）；主要差距集中在**工程基础设施层**——**无版本管理、无自动化回归编排、脚本资产无生命周期治理、数据血缘未机制化**。这四项不解决，现有高质量纪律的**可持续性**存在结构性风险。

## 三、改进建议（按模块分类）

### 模块 A：版本管理与历史追溯

#### A-1 引入本地 git 仓库 【优先级：高】

- **问题背景**：全仓无 `.git`。历史追溯目前完全依赖三套手工机制：`backup/`（9845 文件的全量原件）、`testbed\*.pre-*` 里程碑快照、`backup\before-<事件>\` 事件快照。变更 diff 靠 ad-hoc md5 比对脚本；41+ 篇 `docs` 报告、`glossary/` 术语真源（23,200→37,395 行）、`MEMORY.md` 均无修订历史。
- **改进理由**：行业上版本管理是汉化工程的生命线——译名表被误改、脚本回归、报告被覆盖，都能一条 `git diff`/`git revert` 解决。本工作区已发生过真实风险：①「分支工作区 `军事游戏汉化-1` 删除导致高分辨率线全部脚本丢失」（MEMORY §五第 1 条，靠 exe diff 反推才救回）；②`Get-ChildItem -Include` 静默漏备份 5 个词库产出（docs\51）。这两类事故在 git 下均为零成本恢复。
- **适用场景**：所有文本类资产（`glossary/`、`work/**/*.py`、`docs/`、`peg*/research/`、`.workbuddy/memory/`、各 `README.md`）。
- **实施要点**（避免踩坑）：
  1. **不要把 `backup/`（GB 级原件）、`archive/`（试验 exe）、`poc/`（截图）直接入库**——`.gitignore` 排除或独立管理，仓库只管「会变的东西」；
  2. 二进制 exe 产物不入库（已有 md5 台账 + `archive\` 收档体系，保持现状）；
  3. 提交粒度按「一次真源变更 = 一次提交」（如「地名收敛 12 组新名落盘」），提交信息引用 `docs` 编号；
  4. 纯本地即可，不依赖远端。
- **预估成本**：半天（含 `.gitignore` 设计 + 首次导入）。

#### A-2 弃用/被推翻结论的标记机制 【优先级：低】

- **问题背景**：`docs\59/60` 的结论被 `docs\63` 更正、`patch-lc-time-zh.py` 实测无效仅留档、⛔ 弃用脚本 3 个（`audit_map_quality.py` 等）只记录在 MEMORY。读者按编号顺序读 `docs` 时，无法从单篇头部判断其现行效力。
- **改进理由**：行业文档管理惯例是状态标记。「结论被推翻时写明撤回原因」已是本工作区纪律（§三-8），但目前撤回信息只写在**别处**，不在被撤回文件本身。
- **适用场景**：`docs/` 全部 68 篇。
- **实施要点**：每篇头部加一行状态栏（`> 状态：现行` / `> 状态：§四已被 docs\NN 修订`），只补关键几篇（59/60/61/66 中被后续推翻的段落）。

### 模块 B：质量把控——回归编排、校对与验收

#### B-1 建立统一回归入口（一键全检） 【优先级：高】

- **问题背景**：校验资产非常齐全——`work\audit\progress.py`（全库进度）、`work\glossary\layer_gate.py`（术语门禁）、`work\pegww2\verify_deploy.py`（部署 sha）、`work\_sync-audit\audit_authority.py`（权威核对）、`verify_naming.py`、`residual_scan.py`、`peg_launcher.py --selftest`（267 站点）——但**没有统一编排**。每次收尾要手工按正确顺序逐个跑（层表链三连 `ingest_layers → converge_plan → layer_gate` 也是手敲），漏跑一步即静默失效（docs\49：新增层漏接线 `ovr` 参数导致新层静默失效，正是此类事故）。
- **改进理由**：行业上「回归测试」的意义在于把「人记得跑」变成「机制保证跑」。本工作区的教训清单里，「排除规则 → 登记 → 写入三处必须同时改，否则静默失效」（docs\50）本质上是**缺少一个总装检查器**的问题。
- **适用场景**：每次真源变更后、每次部署前、每个 efile 收官时、以及新会话接手时（快速确认基线）。
- **实施要点**：
  1. 新增 `work\regression.py`（或 `run-checks.cmd`）：按依赖序编排现有脚本，**只调用不重写**；
  2. 输出单一汇总报告（各检查 ✅/❌ + 与上次基线的数字对比，如「权威核对 211→N」），落盘 `work\out\regression-<日期>.md`；
  3. 基线数字存一处（JSON），机器比对而非人眼比对；
  4. 明确「全绿」定义（如：门新增偏离 0 + 部署 sha 一致 + 权威核对不劣化）。
- **预估成本**：1 天。

#### B-2 译文质量校对工具化（译文 linter） 【优先级：中】

- **问题背景**：术语一致性已有门禁（`layer_gate`），但**译文文风/违禁词**的校对仍是人工。已有素材散落各处：BANNED 整串黑名单（`ui-glossary.tsv`）、民国感禁用词清单（`國力/佔領/武裝攻擊/前進觀測官/光榮勝利`）、机翻味/文言腔/过度军事化三组诊断表（`各国军语风格口径.md`）、5 面板名锁定校验、E 标点规范（汉字间多空格检测）。
- **改进理由**：行业上术语 QA 用 CAT 工具（QA 检查器）自动跑；本项目所有规则**已经形式化**，缺的只是把散在生成器里的校验抽成独立 linter。规则化检查比 LLM 校对更可复算、零漂移。
- **适用场景**：任何 `.tsv` 映射表或成品 `.txt` 在入库/部署前。
- **实施要点**：新建 `work\lint_zh.py`：输入文件 → 逐行跑规则（黑名单整串/前缀锁定/禁用词/标点规范/括注格式 `译名(原文)` 半角检查）→ 输出违规清单（文件:行:规则:内容）。规则表与代码分离（沿用 `*-map.tsv`/逻辑分离铁律）。
- **预估成本**：半天~1 天。

#### B-3 溢出与边界的系统化测试 【优先级：中】

- **问题背景**：溢出控制目前是「点位式」（`.ply` 501B、`.xscn` 槽位、`scn20B` 检查），依赖已知约束。未做过**系统化 fuzz**：如超长译名在定长字段的截断行为、生僻字/扩展区汉字在 GBK 转码时的失败模式、`.SCN` 20B intro 名字段的边界。
- **改进理由**：行业经验是「溢出 bug 在玩家手里爆炸，在测试台上便宜」。本工作区曾有教训：「描述框只显示第 1 行起 ⇒ 第 0 行必须是标题，8+1 个场景描述框空白」——若当时有边界用例库可提前发现。
- **适用场景**：每个新格式接入时（新 efile、新 MOD）跑一遍边界用例；翻译长句入库前可跑「长度预检」。
- **实施要点**：建 `work\tests\` 边界用例集（超长串/空串/纯符号/GBK 外字符/裸 CR 换行），一个 runner 对成品目录跑只读断言。不追求全量 fuzz，覆盖已知定长字段即可。
- **预估成本**：1 天（用例可从历史踩坑清单直接转写）。

#### B-4 实机验收流程标准化 【优先级：中】

- **问题背景**：实机验收依赖用户手动跑（纪律 7：严禁自行启动游戏——受沙箱环境约束，合理）。各作验收清单散落（`docs\31` 实机确认清单、`docs\36` 收官核验清单、`docs\64` 判读 6 项），格式不一；PeG-WW2 部署后「待实机复测」从 10-11 挂起至今，**验收未闭环**。
- **改进理由**：行业上「验收清单 + 每项判读标准」是交付环节的标准件。清单不统一导致每次验收都要重新想「该看什么」。
- **适用场景**：每作收官、每次大改部署后。
- **实施要点**：制定统一模板（验收项 / 操作步骤 / 预期 / 实测 / 截图取证），沉淀到方法论技能 `military-game-docs-translation` 的 references；OCR 辅助判读已有雏形（`ocr_shots.ps1`）可纳入流程。**注意**：自动启动游戏仍禁止，仅把「用户跑完之后的判读」半自动化。

### 模块 C：工具与脚本资产管理

#### C-1 脚本生命周期治理（探索/生产/弃用分流） 【优先级：中】

- **问题背景**：`work/` 下 300+ 个 Python 脚本（peg 126 / pegww2 109 / glossary 74）。混放形态：①探索迭代版 `work/xscn/_analyze-openpg.py` 至 `_analyze5`、`_sync-audit/audit_brief_map.py` 至 `map5` 共五代；②已弃用脚本（⛔ 3 个）仅记录在 MEMORY，文件原地无标记；③根目录散件 `map1-4.tsv`、`out-diag.txt`。
- **改进理由**：行业工程惯例「prod 与 scratch 分离」。迭代版混放的直接代价：新会话（或几周后的自己）无法判断该用 `map` 还是 `map5`；弃用脚本被误跑会造成污染（弃用原因正是校验不可靠）。
- **适用场景**：`work/` 全目录。
- **实施要点**：
  1. 建 `work\_scratch\`（或按子目录建 `_attic\`），迁移迭代版与一次性诊断脚本；
  2. 弃用脚本原地加头部注释 `# ⛔ DEPRECATED: 原因见 MEMORY §二，勿用` 或移入 attic；
  3. 每个子目录补一份 `SCRIPTS.md` 索引（脚本名/用途/输入输出/状态）——`peg\README` 已有速查表可作模板，扩展到全仓；
  4. 根目录散件归位到对应 `<tag>/out/`。
- **预估成本**：半天（纯移动 + 写索引）。

#### C-2 统一命令行入口 【优先级：低】

- **问题背景**：常用操作是多脚本串联手敲（「每完成一个 efile 跑四连：`build_dict && build_root_dict && build_prose_dict && build_master`」；层表链三连；`--promote`/`--deploy` 分步）。参数约定各脚本自成一套（部分默认 dry-run、部分 `--apply`、部分 `--promote`）。
- **改进理由**：降低新会话/新作接手成本；与 B-1 回归入口同构，可合并实施。
- **适用场景**：高频重复序列。
- **实施要点**：`work\run.py <task>` 形式的任务路由（`regression` / `rebuild-glossary` / `layer-chain` / `deploy-pegww2` …），每个 task 就是现有脚本的顺序调用。**不重写脚本本身**。
- **预估成本**：与 B-1 合并实施。

#### C-3 运行环境固化 【优先级：中】

- **问题背景**：已发生环境事故：旧托管 venv 失效（被迫切 `C:\Python314\python.exe`）；`PYTHONIOENCODING`/`PYTHONUTF8` 不设则脚本崩（✅/⭐ 撞 GBK 控制台）；PowerShell 管道包原生 exe 报 Access denied；逆向工具依赖 capstone 等包但无依赖清单。
- **改进理由**：环境不可复现 = 「跑过了」不可复现。对以「可复算」为核心价值的工作区，环境本身应纳入可复算范围。
- **适用场景**：换机、重装、新会话首次跑脚本。
- **实施要点**：①重建 venv（用 `C:\Python314` 也行，但**固定并写死在文档**）；②生成 `requirements.txt`（`pip freeze`）；③写一个 `env.cmd`（设 UTF-8 环境变量 + 激活）供所有文档引用；④MEMORY/README 的「环境」段落指向这一处真源。
- **预估成本**：半天。

### 模块 D：数据治理——真源与血缘

#### D-1 生成器「命中来源」溯源落地 【优先级：高】

- **问题背景**：docs\49 教训（原文）：「生成器『查表 → 写盘』应记录每行**命中来源**（哪张表/哪一行），否则『**成品对而真源错**』的倒挂极难发现（`docs\47` 就把它误判成『词库滞后于成品』，实为第三真源未入库）」。此教训已发生、已定性，但**机制未落地**——当前生成器仍是无溯源的查表写盘。
- **改进理由**：数据血缘（lineage）是数据工程的标准能力。本工作区真源已有**四层**（per-file 行号级覆盖 > 整串精确匹配 > 原样保留 + 层表/覆盖表/映射表多张），层级越复杂，无溯源的代价越高——docs\47 误判已实证。
- **适用场景**：`gen_scn_zh.py`、`gen_scn.py`、词库 build 链等所有「查表→写盘」生成器。
- **实施要点**：生成器每次运行同时输出 sidecar 溯源文件（`成品文件.tsv.lineage`：行号 / 命中表名 / 表内行号 / 键），或至少聚合统计（每行来源计数）。审计时可用「成品 vs 溯源」对账，替代「成品 vs 真源」的猜测式对账。
- **预估成本**：1 天（改生成器 + 存量一次回放生成溯源）。

#### D-2 真源清单「单一登记表」 【优先级：中】

- **问题背景**：真源体系庞大：`standard-glossary.tsv`、`master-glossary.tsv`（四层）、`common-glossary.tsv`、`layers/`（7 张表）、`scn-place-override.tsv`、`_scn-file-overrides.tsv`、各作 `*-map.tsv`、`master-overrides.tsv`、`override.tsv`（派生）……哪张是真源、哪张是派生物、谁消费谁，全部记录在 prose 文档里，无机器可读的总账。
- **改进理由**：docs\50 教训「新增一层/一条排除规则，牵动『排除规则 → 登记 → 写入』三处，必须同时改，否则静默失效」——本质是依赖图未显式化。一张登记表可以让「这层被谁消费」一查便知。
- **适用场景**：任何新增真源表、重构词库时。
- **实施要点**：`glossary\SOURCES.tsv`（表路径 / 真源 or 派生 / 上游 / 下游消费者脚本 / 优先级层级），由人工维护一次即可；B-1 回归入口可顺带校验「登记的消费者都能找到表」。
- **预估成本**：半天。

#### D-3 层表「文件维度」缺口的显式决策 【优先级：低】

- **问题背景**：层表主键 `(en, 层, scope)` 无文件维度，导致 28 行「同键多译」（同一英文在不同文件取值不同，如 `Avalanche`/`Dessau`）只能落证据表，无法在层表内表达；正确出口是 `scn-place-override.tsv`（按场景词干）。
- **改进理由**：这是**已知且已分析**的理论缺口，用户已裁定「不做」（修层表键对门影响 0 条）。本条不是要求实施，而是建议把「同键多译 → 必须走覆盖表」这条路由规则写进 `glossary\README.md` 的操作指引，避免未来误改层表主键。
- **适用场景**：词库维护者（未来的自己）。

#### E-2 格式规格的机器可读化 【优先级：低】

- **改进理由**：行业上格式规格是 RE 项目的核心资产，通常以 IDL/struct 定义或单一偏移表文件维护（本工作区已有雏形：`res_diff_v4.tsv`、`panel_table_manifest.tsv`、`ui_layout_v9.tsv`——证明该模式有效）。

#### E-3 新会话「冷启动」成本压缩 【优先级：低】

## 五、结语

本工作区最大的优势是**纪律密度**——每个环节几乎都有「踩坑 → 定纪律 → 成文」的闭环，这在个人汉化项目中罕见。最大的风险是**纪律的执行依赖记忆与手工**：无版本管理意味着一次误操作可能摧毁多日成果；无回归编排意味着纪律漏跑是静默的；无溯源意味着真源与成品的对账永远靠猜。第 1 批三项建议的本质，是把「人的纪律」升级为「机制的纪律」——与本项目一贯的「唯源 + 可复算」哲学完全同构：**代码能保证的事，不依赖人记得**。
