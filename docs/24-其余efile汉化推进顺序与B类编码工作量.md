## 一、裁定：沿用既有 efile 优先级，不按问题集中度插队

`docs\23` 结尾曾建议「从 KAISER 开刀」（德语最集中、单点收益最大：1,198 / 4,433 = 27%）。
**用户裁定：按原来的 efile 优先级排。**

### 为什么不按集中度开刀（三条硬理由）

| # | 理由 | 具体后果 |
|---|---|---|
| 1 | **交付单位是一个 efile，不是一个问题** | 验收必须整目录切到该 efile 才能实机看；只做完它的 `equip.txt` 而 `SCENARIO` 还是英文 ⇒ 玩家看到的是**中英混排**，比全英文更糟 |
| 2 | **问题密度 ≠ 重要度** | KAISER 占 27% 只因为它是**一战德军 mod、作者用德语命名**；密度反映的是该 mod 的**作者语言习惯**，与玩家覆盖面无关 |
| 3 | **打乱顺序会让进度表失去可比性** | 出现"跳号完成"的半成品模块后，进度表无法回答"还剩几个 efile"，也无法按序交接 |

> **一句话判据**：这个顺序是**问题**决定的，还是**目标**决定的？
> 批量问题的清单要**按目标（efile/模块/版本）重排为批次**，而不是按问题密度排序。

## 四、每批的交付物定义（一批 = 一个 efile，一次做完）

| 层 | 动作 | 落点 |
|---|---|---|
| 根级 | 建 `TEXT-ZH\equip.txt` / `names.txt` / `nations.txt` / `strings_efile.txt` | **不动原文** |
| 场景文本 | 建 `TEXT-ZH\SCENARIO\*.txt`（或覆盖 `<efile>\SCENARIO\` 并备份） | 按 §二 目录矩阵 |
| 数据类 | `SCENARIO\*.xscn` 尾部串区字节级回写 | **只认 `<efile>\SCENARIO\`** |
| 简报 | `TEXT-ZH\SCENARIO\*.ply` | LangDir |
| 位图 | `OPENGUI\hex_text.png` / `mouse_*.png` | 仅文字型（`Clu` 跳过） |

**每批必做的三项校验**：
1. 出稿 **GBK(936) / 无 BOM / CRLF**，中文侧行数与原文**逐行对齐**；
2. `.xscn` 用独立解析器复核（条目数/组表/长度自洽，异常 0）；
3. `.xscn` ↔ `.txt` 硬桥校验零新增（`bridge_check.py`）。

## 五、⚠️ 中文侧的硬约束（每批都会撞到）

**GBK 装不下西文变音符**：`'Légion'.encode('gbk')` 直接抛异常。
往中文侧写任何带变音符的西文前**必须二选一**：

- **折写成 ASCII**（`ä→a`、`é→e`、`ü→u`、`ö→o`、`ñ→n`、`ç→c`）—— 用于人名/型号；
- **译成中文**（`Fallschirmjäger`→伞兵、`Légion Etrangère`→外籍军团）—— 用于兵种/编制。

`glossary-orig-charset-fix.tsv` 已备好 `ASCII折写` 列，可直接取用。

### 六之一、⚠️ 排期依据要改：B 类行数 ≠ 该 efile 的工作量（B1 实测教训）

上表的"行数"用的是 **B 类编码行数**，它**只统计带变音符的行**，完全不反映 efile 的真实体量。
`EFILE_AG` 被排在 B1（29 行"最小"），实测开做才发现它并不小：

| `equip.txt` | 734 行 / 211 唯一 | 已汉化 |
| `names.txt` | **2449 行 / 951 唯一** | 已汉化（古代人名，库命中率仅 1%，**全部新译**） |
| `nations.txt` | 112 行 / 48 唯一 | 已汉化 |

| `SCENARIO\*.txt` | **286 个 / 142 KB** | 含《高卢战记》英译散文（`csr` 族 39 个 41 KB） |
| `SCENARIO\*.xscn` | 86 个 / **6009 条目**（唯一 2335） | 组 0 地名 186 唯一；组 1 单位/部落 2237 唯一 |
| `SCENARIO\*.ply` | 1 个 | 51 B |

**⇒ 排期/估工必须按「全 efile 量测」（根级行数 + 场景文件数 + 条目数），
B 类编码行数只能作为"该 efile 有没有变音符问题"的参考，绝不能当工作量指标。**

各批次开工前，先做一次"全 efile 量测"再谈排期。
