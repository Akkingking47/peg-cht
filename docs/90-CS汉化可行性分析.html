John Tiller's Campaign Series 中文本地化可行性分析

一、可行性结论

总体判定：技术可行（有条件）。 本系列三作共用同一套文本渲染机制：文本走 Win32 GDI 的 TrueType 系统字体（MS Sans Serif / Times New Roman），绝大多数用户可见数据（单位名、场景名、战役、描述）存在于纯文本外部文件中。2.05 版（2025-09-08 重编译，工具链由旧 Borland OWL 换为 MFC9 / MSVC2008，主引擎约 1.6MB）后，三作引擎不再是字节一致（ef.exe 1,609,488 B；wf.exe / risun.exe 1,610,000 B，Rising Sun 引擎改名为 risun.exe），但字体调用与 GDI API 与旧版完全相同，故汉化路径不变。这两点决定了中文汉化在技术上不存在根本性障碍。

落地需要同时满足四个条件，缺一不可：

  • ① 字体补丁：把 exe 中硬编码字体名替换为中文字体（如 SimSun 宋体 / SimHei 黑体），确保渲染链路支持 CJK 字形。
  • ② 中文代码页运行环境：引擎使用 *A 系列 ANSI API（CreateFontA/TextOutA/DrawTextA）并按系统 ANSI 代码页读取文本，需在 cp936（中文） 下运行（中文 Windows 或 Locale Emulator / NTLEA 强制）。
  • ③ 海量文本翻译与 GBK 重编码：约数千个纯文本文件需按字段抽取、翻译、decode(cp1252)→encode(GBK) 回写。
  • ④ 少量含英文 baked 图的重绘：6–8 张 8-bit BMP（主菜单、报告框、控制条、教程、胜利画面等）内嵌英文文字，需图形重绘或替换。

置信度：文本类资源汉化与中文渲染路径 = 高；含字图重绘 = 中（技术简单、工作量中等）；EastFont.BMP 是否被某处文字使用 = 待运行时确认（当前证据指向"未被引用"）；存档兼容 = 待实测。

2.2 实测证据摘要

  • 引擎（2.05 重编译） 三作主引擎于 2025-09-08 统一重编译，工具链为 MFC9 / MSVC2008（导入 mfc90.dll/MSVCP90.dll）。大小不再一致：ef.exe 1,609,488 B、wf.exe / risun.exe 1,610,000 B；Rising Sun 引擎改名为 risun.exe。三作字体调用与 GDI API 一致（均已复核）。
  • 渲染 API（2.05 重测） ef.exe / wf.exe / risun.exe 均导入 CreateFontA、TextOutA、ExtTextOutA、DrawTextA —— 全部 ANSI 版本（无 ...W 宽字符版），按系统代码页渲染，故方案依赖 cp936。
  • UTF-16 资源 670 条 UTF-16LE 串（旧版数值），含 &File &Help &Turn &Units &Victory... Exit program 等菜单项，以及 UNITLISTDIALOG / VICTORYDIALOG / TARGETDIALOG 等对话框标识（2.05 重编译后需按新 exe 重新抽取并确认）。
  • 数据文件 Army00.oob 含 Rifle Corps / Tank Brigade / Anti-Tank Regiment 等单位名；Agard.scn 含 25 Kilometers to Budapest 场景标题 —— 皆为纯文本、可直接翻译。
  • EastFont.BMP 未引用 对 East Front 目录下所有 exe/dll 做字节扫描，未发现 "EastFont" 字样；字体名（MS Sans Serif×8 / Times New Roman×7 / System×2，ASCII 字面量）出现在 ef.exe 及 MFC9 框架中。结论：当前构建里 EastFont.BMP 疑似遗留/未用资产，文字渲染依赖 TrueType 系统字体。
  • 编码隐患 1299 个文本文件中 150 个含 cp1252 变音字符（如 Günther, Küchler, Skijäger, Lübbenau, Batallón, Pätzold, Säiniö, Häkkinen, Björkman，2.05 重测）。在 cp936 下这些单字节会变乱码，必须 decode(cp1252)→encode(GBK) 转换。

三、East Front 中文渲染专项评估

是否支持中文 / 双字节渲染？ 引擎本身不"内置"中文，但它通过 CreateFontA 请求系统 TrueType 字体并以 ANSI 方式绘制。TrueType 字体内部是 Unicode，能否显示中文取决于两件事：(a) 请求到的字体是否含 CJK 字形（把 MS Sans Serif 换成 SimSun/SimHei 即可）；(b) 传入的文本字节是否被按正确代码页解读（必须 cp936）。二者齐备则中文正常显示。

当前字体与字符集：硬编码 MS Sans Serif（UI）与 Times New Roman（报告/地图文本），均为西文 TrueType，不含中文 glyph；字符集参数由 CreateFontA 的 fdwCharSet 决定，该值未以字符串形式出现，需反汇编确认（推测为 ANSI_CHARSET/DEFAULT_CHARSET）。GBK 与 DEFAULT_CHARSET 的 TrueType 字体搭配时，GDI 会按字体 Unicode 映射渲染，对中文友好。

GBK 兼容性：可行，但前提是运行于 cp936。若保持英文系统(cp1252)运行，GBK 双字节会被误读为西文 → 乱码。因此方案不是"让引擎支持 GBK"，而是"让引擎在中文代码页下用中文字体渲染"。

需要替换字体 / 自制字体 / 改程序？ 替换字体名即可，无需自制字体，也无需改程序逻辑。 用十六进制编辑器把 MS Sans Serif\0 替换为 SimSun\0（更短，零填充），Times New Roman\0 同理。若反汇编发现 charset 参数强制为某西文值，再针对性 patch 该字节为 134 (GB2312_CHARSET)。

五、最小可行验证（MVP）

⚠️ 本 MVP 在执行阶段只作用于备份副本，不触碰 Program Files 下的原文件；改 exe 前必须先做全量备份。下面给出可立即执行的方案，是否启动实机由你确认。

5.1 步骤

  1. 备份：把整个 East Front\ 复制到隔离工作目录（如 work\jtscan\MVP\）。同时单独备份 ef.exe + 一张 .oob（如 Army00.oob）+ Menu Screen.BMP。
  2. 选样本：① 一份 .oob 中 3–5 个单位名（如 Rifle Corps→步兵军, Tank Brigade→坦克旅），按 decode(cp1252)→zh→encode(GBK) 回写；② 在备份副本的 ef.exe 中把 MS Sans Serif 替换为 SimSun（零填充），并把一处 UTF-16 菜单串（如 Exit program）改为 退出程序。
  3. 字体/代码页：在 cp936 环境（中文 Windows，或 Locale Emulator 以中文区域启动备份副本的 ef.exe）下运行，进入任一场景，查看单位信息面板与菜单。

5.2 成功判定标准

  • ✅ 单位信息面板出现中文单位名且无乱码（非 ? 或 □）；
  • ✅ 菜单出现"退出程序"等中文且无崩溃；
  • ✅ 原英文其他处仍正常显示，无报错弹窗。

5.3 失败回滚

  • 任何异常：用备份的 ef.exe / .oob 直接覆盖副本即可（本 MVP 不改动原目录，原目录天然安全）。
  • 若中文显示为方块(□)：说明字体未生效 → 检查字体名写入是否准确、运行环境字体是否安装。
  • 若中文显示为问号(?)：说明代码页不对或字节被当作 ASCII → 确认 cp936 运行 + GBK 编码。
  • 若启动崩溃：说明 exe 字节改坏 → 还原 exe，改回字体名或缩小改动范围。

5.4 后续决策条件

  • MVP 全部 ✅ → 进入第六节的完整分阶段实施。
  • 仅数据文件中文成功、exe 菜单未变 → 排查 Resource Hacker 重编译 / UTF-16 串是否生效。
  • 出现方块/问号 → 优先解决字体名与 cp936 环境，再扩大范围。
  • 若发现某处文字（如地图标签）不随字体替换而变化 → 指向 EastFont.BMP 被使用，回到障碍#6 专项排查。

八、"世纪雷神曾发行完全汉化版"线索的价值与遗留核实

参考价值（可作为"已有人走过这条路"的强证据）：商业汉化版的存在，说明本系列在技术上不存在根本性不可逾越障碍——中文渲染、海量文本汉化、含字图处理都被实际做成过。这能显著降低试错成本，并暗示可行路径就是"字体替换 + 中文代码页 + 全文本翻译（+可能的图重绘）"组合。

但不得视为已验证事实：本安装是 TalonSoft/Matrix 英文原版，我未拿到其汉化版文件，无法确认具体手法。以下为可进一步核实的遗留资源（建议动手前核实，能大幅缩短试错）：

  • ① 世纪雷神汉化版的 exe/dll 与数据文件样本：与本版做字节/文件对比，直接看出改了哪些字节、哪些文件、是否动过 EastFont.BMP。
  • ② 是否随包提供语言选择 / 注册表或 ini 设置：本安装 Setup.ini 有 EnableLangDlg=Y（语言对话框开关），但其确切功能未验证，可能关联一个本安装未随附的语言包机制——这正是世纪雷神版最可能利用的入口。
  • ③ 是否重绘了 BMP / 是否要求中文系统或外挂(AppLocale/LE)：决定了我们的阶段 4、阶段 5 是否与其一致。
  • ④ 其运行环境要求：是否强制中文系统或带启动器，关系到部署方式。

说明：以上①②③④均为"推测性待核实项"，未作为本报告可行性判定的依据；本报告的"可行"结论仅建立在本安装实测证据之上。

十、2.05 版更新重新评估（2026-10-20 补充）

背景：用户将游戏更新至 V2.05（2025-09-08 构建）。重新核验目录与三作主引擎二进制后确认：本次"更新"实为 Matrix 的 2025 年整包重编译/重发（V2.03 / 2.04 / 2.05 均在 2025 年，构建日期均为 2025-09-08），并非单纯补丁。更新日志（changelog_205.txt）明示 2.05 仅"修订胜利对话框以允许更大数值"，2025 系列改动集中在场景/数据/显卡兼容，无任何字体、编码或语言相关条目。

变化（实测）：

  • 工具链更换 旧版为 Borland OWL；2.05 主引擎导入 mfc90.dll / MSVCP90.dll（MFC9 / MSVC2008），依赖 VC2008 运行库（应在 redist\ 随包，或测试机另装 vcredist_x86）。
  • 引擎体积与一致性 主引擎由 1,085,440 B 增至约 1.6MB；三作不再字节一致：ef.exe 1,609,488 B、wf.exe / risun.exe 1,610,000 B（相差 512 B，应为各作战区资源差异）。
  • Rising Sun 引擎改名 因与 NVIDIA 命名冲突导致地图变形，引擎由 rs.exe 改名为 risun.exe（更新日志明示）。
  • 新增基础设施 JSGME.exe（Jones Soft 通用 Mod 管理器）+ Mods/ / User_Mods/ 目录 + campres.exe/cdd + JTCSUpdate.exe。

未变（汉化方案仍成立的关键）：

  • 渲染机制不变 三作仍仅导入 CreateFontA / TextOutA / DrawTextA / ExtTextOutA（ANSI），仍硬编码 MS Sans Serif(×8) / Times New Roman(×7) / System(×2)（ef.exe 实测；另两作同机制）。EastFont.BMP 仍 0 引用。
  • 清单已排查（排除新陷阱） 解析 ef.exe 内嵌 manifest：存在（VC90 CRT 依赖），但未声明 activeCodePage=UTF-8、未声明 dpiAware、无 <language>。即进程采用系统 ANSI 代码页（cp936 下即 GBK），不会把 GBK 数据误当 UTF-8——该潜在新风险已排除。
  • 数据编码不变 文本文件仍为纯文本；2.05 重测 1299 个文本文件中 150 个含 cp1252 变音字符（Pätzold / Günther / Säiniö / Häkkinen / Björkman 等），decode(cp1252)→encode(GBK) 策略照旧。

对原方案的三处调整：

  1. 逐作各打一次 exe 补丁：三引擎不再字节一致，字体名补丁用字符串搜索（非固定偏移）即可兼容各 exe；Rising Sun 注意目标是 risun.exe。
  2. 借 JSGME 部署数据文件：翻译后的 .oob/.scn/.org 等可做成 JSGME Mod（Mods/ 下），开关即生效、不破坏原文件；exe 字体补丁仍须单独处理（JSGME 不改 exe）。
  3. 确保 VC2008 运行库：新引擎依赖 mfc90 / msvcp90，测试/部署机需有对应 vcredist，否则游戏根本无法启动（与汉化无关，但是运行前提）。

结论：2.05 更新不改变汉化可行性——文字渲染路径与字体机制与旧版完全一致，且已确认无 UTF-8 代码页陷阱。第一～九节的方法论全部有效，仅上述三处部署细节需按 2.05 调整。下一步仍从第五节 MVP 起步（备份副本 → 字体名替换为中文字体 + cp936 启动 → 验证中文上屏）。
