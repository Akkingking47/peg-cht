## 二、v4 达成了什么

- **地图视口确实放大到 1024 宽**：地形一直铺到内容 x≈1016，v3 里「地图止于 800、右侧全是花屏」的现象消失 ⇒ 用户的目标「一屏看得更多」在**地图这一层已经成立**。

## 三、v4 没做成什么（用户看到的「变这样了」）

1. **工具列被横向拉伸**：v3 里按钮是内容 x 762..787 的 26×26 小方钮；v4 里同一列变成内容 x **800..985** 的 186×26 胶囊条（绿框变粗、图标被横向涂抹成拖影），竖直位置与行距不变。
2. **内容 986..1011 什么都没画**（那是地形）——而这正是 v4 把按钮记录改成的坐标。
3. **右侧 986..1023 与底部 740..768 从未被绘制**：花屏（品红/绿横条、黑白竖纹）+ 纯黑。
4. **底部状态条没有下移**：v3 与 v4 的「步兵 / M2A3 布萊德雷 / 工事 1」都在同一高度（约 shot y 596..618）；而 v4 明明把 `.data` 里那条底部条记录 `y/bottom += 168`。

## 四、根因（高置信）：界面位置是**代码运行时现算**的，v4 只改了数据记录

### 4.1 证据一：面板矩形由代码硬编码 799/571 生成

`0x41C4A6`–`0x41C520`（母本，反汇编原文）：

```
0x41c4cd  mov dword ptr [ebp-0x10], 0x16      ; 22 = 顶栏高度
0x41c4d4  mov dword ptr [ebp-8], 0x23b        ; ★ 571  ← v4 未改
0x41c4db  mov dword ptr [ebp-0xc], 0x31f      ; ★ 799  ← v4 未改
0x41c4e2  mov edx, dword ptr [0x676904]       ; DirectDraw 表面
0x41c4eb  mov word ptr [ebp-0x18], 0xb4       ; 180 = 面板宽
0x41c502  movsx edx, [ebp-0x18] ; mov eax, [ebp-0xc] ; sub eax, edx ; add eax, 1
          mov [ebp-0x14], eax                 ; left = right - 180 + 1 = 620
0x41c520  call 0x4235E5                       ; 传入 {left=620, top=22, right=799, bottom=571, 表面}
```

⇒ 右侧整块 UI（7 个工具钮 + 单位信息控件）都在这个面板里，面板的右边/下边**就是屏幕边缘 799/571 的硬编码值**。v4 改了记录、没改这两个立即数。

### 4.2 证据二：面板里逐控件定位的循环，把记录的**绝对坐标换算成面板相对坐标**

`0x41C528`–`0x41C57D`：

```
0x41c528  mov word ptr [ebp-0x1c], 0x20       ; 从控件序号 32 开始
0x41c540  cmp eax, 0x27                       ; 到 39（共 8 个）
0x41c549  imul ecx, ecx, 0x24                 ; 记录步长 36
0x41c54c  movsx edx, word ptr [ecx + 0x490474]; 记录.y
0x41c553  sub edx, dword ptr [ebp-0x10]       ; y - 22
0x41c55e  movsx ecx, word ptr [eax + 0x490472]; 记录.x
0x41c565  sub ecx, 0x26c                      ; ★ x - 620（面板左边）
0x41c575  call 0x425407                       ; (面板结构, 序号, x-620, y-22)
```

⇒ 记录被当作**面板内相对坐标**消费。v4 把记录 x 改成绝对坐标 986、代码却仍按旧面板（左 620）换算，画的与点的就此错位。

### 4.3 证据三：未生效的位移

底部状态条记录（`0x4A24F0 {0x1820,10,576,790,594}`）在 v4 里被改成 `y/bottom = 744/762`，实机却在原位（≈576）⇒ 该记录同样不直接决定绘制位置。

### 4.4 控件记录表的真实布局（已实证，供 S3 使用）

- 基址 **`0x490470`**、步长 **`0x24`(36)**、每条 5 个字段：
  `+0 u16 flags`、`+2 i16 x`、`+4 i16 y`、`+6 i16 right`、`+8 i16 bottom`
- 命中测试函数 **`0x43FF28(widget_array, x, y)`**：`movsx ecx,[ebp-8]; imul ecx,ecx,0x24; mov edx,[0x4cce2c]; … [ecx+2]/[ecx+6] 比 x、[ecx+4]/[ecx+8] 比 y`，命中写 `[0x4cce30]`
- **`0x43FE70(array)`** = 切换当前控件数组（`[0x4cce2c]`），并清 `[0x4a031c]` 高亮
- 数组 0 号 = 地图视口 `{1, 0, 22, 1023, 740}`（v4 已按 1024×768 改好）
- 1..7 号 = 工具钮 `{0x1045, x 762→986, y 71/428/140/212/284/356/527, right 787→1011, bottom y+25}`
  ⭐ **行距是 72，而行距为 36 的胶囊另有来源** ⇒ 画面里那条周期 36 的胶囊列**不是**这 7 条记录直接画出来的
- 8..31 号 = `flags=0x20` 的 18×18 小件（x=637 / 728，y 每 72 一组，各 6 行）
- 32..37 号 = `flags=0x1820`(6176) 的 118×56 件（x 633..750，y 每 72，共 6 行）
- 38..39 号 = `flags=1` 的 16 宽小件（x 686..702）

### 4.5 未修复的「旧分辨率」落点（v4 漏掉的部分）

来自 `work\peg\out\res_missing_candidates.tsv`（6361 B，列：section/imm_va/ins_va/file_off/mnemonic/instruction/old/suggested/kind）：

- **面板/屏幕矩形代码**：`0x41C4D4`(571→740)、`0x41C4DB`(799→1023)、`0x41C565`(620→844，仅在记录仍是相对坐标时才需要)
- **视口裁剪运算 6 处**：`0x44C730` `0x44C777` `0x44C869` `0x44C8B0` `0x44CC67` `0x44CCAE`
- **屏幕边框 2 处**：`0x44C5CC`(push 570→738)、`0x44C5D1`(push 796→1020)
- **运行期构造矩形对**：`0x41C4D4/DB`、`0x42E497/0x42E49C`、`0x45A0F2/0x45A0F7`、`0x45A94B/0x45A950`
- **坐标夹取 7 处**：`0x4567C4` `0x4567DE` `0x4568E2` `0x4568FC` `0x45696F` `0x456984` `0x456A3F`
- **旧「800×600 屏幕记录」19 条仍未改**：`flags=1` 的 `{0,0,800,600}` 9 条（`0x48E1FC` `0x48E4F4` `0x490F9C` `0x491CDC` `0x49297C` `0x498160` `0x4A0040` `0x4A1378` `0x4AB0CC`）+ `flags=0x20` 的 10 条（`0x48F550` `0x493B70` `0x494814` `0x4973C4` `0x4A17B8` `0x4A1A7C` `0x4A3B04` `0x4A60AC` `0x4A9310` `0x4A9610`）
- v4 已改、但存在**双位移风险**：163 条 `dx=+224`、2 条 `dy=+168` 的记录 —— 一旦代码里的 799/571 也被改成 1023/740，这些记录会被再算一次位移。

### 4.6 本轮否定/确认的假设

- ❌ 「v4 的 stride/pitch 不同步」：`0x410DB2 push 0x640` 只是 `memset(0x69d020, -1, 1600)` 的 4×400 定长表；`0x4426F7 push 0xc80` 是 `memset(0x641620, 0, 3200)`；`0x4672D3/0x46799B add 0x4b0` 是导入函数的参数偏移。唯一真行距在 BMP 导出函数（`0x4144A9` Lock … `0x4147BD` Unlock，文件头 `'BM'`、24bpp、`imul edx,edx,0x320`）⇒ 只影响导出图，不影响画面。
- ✅ 「v4 只改数据、没改生成数据的代码」：三条独立证据（4.1/4.2/4.3）互证。
- ✅ 记录表布局与命中测试函数（4.4）。
- ❓ **仍未定位**：画面里内容 x 800..985（宽 186）、行距 36 的胶囊列到底由哪段代码画（宽度与行距都不符合 v4 的记录）⇒ v5 之后可能仍需一次取证。

## 五、下一步（S3 / v5）建议

**原则：改「生成数据的代码」，而不是改「被生成的数据」；并处理双位移。**

1. 补 `0x41C4DB`(799→w-1)、`0x41C4D4`(571→h-28)、`0x44C5D1`(796→w-4)、`0x44C5CC`(570→h-30) 与 6 处视口裁剪运算；
2. 评估 163+2 条记录位移是否需要**回退**（若代码改成 1023/740 后记录仍按 dx/dy 叠加，会二次位移）；
3. 19 条 `{1|32,0,0,800,600}` 屏幕记录按语义改成 `{1|32,0,0,1023,740}`；
4. 产物必须由**用户实机试跑截图**（我方严禁自行启动游戏）；
5. 建议先做**最小诊断版**：只补 4.1 的两个立即数，预测「工具列归位、胶囊拉伸消失」；一次改动一次判读，比一次全改更容易定位残余问题。
