## 一、方法论：逆向一个未知二进制层

### 1.1 唯一自洽判据

**「解析位置 == 文件长度」是唯一可靠的解析终点判据。**

- `.xscn` 串区：`cnt == 0` 是**合法空组**，不是结束信号。旧规则「`cnt<=0` 即 break」让 AG 低估 1,143 条。
- `.xsch`：最后一条记录结束处必须 == 文件长度。扫描「候选位置自洽」**会误判**（正文里凑巧的字节）。

### 1.2 定长槽 > 自适应扫描

`.xsch` 的槽A 全库恒定 104 B。**一旦确定是定长，就删掉所有扫描逻辑**：
"遍历候选位置找 tail" 会命中正文里的巧合字节；直接 `record_hdr + 12 + 104` 取 tail 则全对（52/52）。

> **教训**：自适应/模糊解析在**已知布局**时应立即退化为确定性解析。模糊规则看起来更"通用"，实则是误判之源。

### 1.3 宽容度是双刃剑

- 判头条件 `h[0] in (0,1)` **太松** ⇒ 匹配到正文字节 ⇒ 52 个文件全失败。
- `[8]==6` **太紧** ⇒ 漏判 `aochoice02`(7) / `bkbkchoice`(0x0FA0)。
- 真相：`[8..12]` 是 **u32**（值 6/7/4000），不是魔数。

> **教训**：常量字段（magic）要**先量测全样本的取值范围**，再定判据；不要凭单一样本猜。

## 二、判「是否已汉化」的判据纪律

### 2.1 三种伪进度（必须挡）

| 伪信号 | 现象 | 挡法 |
|---|---|---|
| **假汉字** | 裸 `decode('gbk')` 把 cp1252 高字节解成汉字（`Ôþ`→`轧`） | GB2312 字节范围 `0xB0A1–0xF7FE` |
| **复制冒充翻译** | `TEXT-ZH` 副本逐字节 == 原文 | 直接比 md5/bytes |
| **恒等映射** | 映射表 `src==dst` 被算成"已处理" | 建表时过滤 `b != a`；**判进度只读文件** |

### 2.2 ⭐ 本轮新踩：`TEXT-ZH` 侧必须按 `gbk` 解

审既有 efile 的 `names.txt` 时，我按 **cp1252** 解 `TEXT-ZH\`，得出"含汉字率 0%"的**假结论**，
差点据此定错口径（以为既有人名不译）。改用 `gbk` 解后真相：

| efile | 实名含汉字率 |
|---|---:|
| AG | 56% |
| OPENPG | 96% |
| NASHORNPBEM | 100% |

> **教训**：**原文侧 cp1252、中文侧 gbk** 是两条铁律，混用会双向误判。
> 判断"中文侧是否已译"要用 gbk；判断"原文侧是否有变音符"要用 cp1252。

## 三、提速：跨 efile line-aligned 复用

### 3.1 做法（AO 批主力）

对每个已汉化 efile，`zip(orig(cp1252), zh(gbk))` 建 `src→dst` 表 ⇒ 新 efile 查表复用。
AO 实测：`equip` 复用 77 + policy 144、`names` 复用 53 ⇒ **复用率 20–30%**。

### 3.2 三个硬约束

1. **行数不齐 ⇒ 整体弃用**。OLGWW2 `names.txt` orig 2261 / zh 2264（+3 行）⇒ 错位会批量错译，**弃用该 efile**。
2. **先验 `len(orig)==len(zh)`** 才建表。
3. **key 原样匹配**（含尾随空格 `Vogel `、变音符 `Müller`）；`strip()` 会漏配。

> **价值不止省力**：复用保证同一人名/装备在**不同 efile 同译**，是口径一致性最便宜的来源。

## 四、结构坑：`strings_efile.txt` 的裸 `\n`

注释块第 6 行夹着**跨行的裸 LF 段**：

```
*------…------\r\n      ← 第5行末 CRLF
\n                       ← 裸 LF
* (units) … redefined\n
[classes]\r\n
```

⇒ `split('\r\n')` 后第 6 个元素是**多行字符串**。

- **正确回写**：`'\r\n'.join(lines)`（裸 `\n` 留在元素内）。
- **验收**：回写后 `LF 计数`/`CRLF 计数` 与原文件**完全相同**（AO 56 / 54）。
- **根因定位**：这正是某 efile「按行对齐整体偏移 1 行」(`align False 150/151`) 的成因。

> **教训**：对任何"按行处理"的 efile 文本，**先确认两文件用同一分片口径**；`split('\r\n')` 是唯一安全选择。

## 五、分层口径（AO 批确立）

| 层 | 口径 |
|---|---|
| `equip.txt` | **型号保留原文**（交叉核对既有 4 efile 一致）；只译兵种/编制/舰级/科幻单位 |
| `names.txt` | 实名**音译**；`???`/`Ant #NNNN`/`#rrggbb`/`Classified` 保留 |
| `nations.txt` | 阵营/国名译；`???` 保留 |
| `strings_efile.txt` | 全表译；`[...]` 段头 / `*` 注释 / **行序**保留 |
| 场景 `.txt` | **`<ef>N.txt` 是标签文件**（首行标题 + **番号缩写** + 地名）⇒ 番号保留；散文全译 |
| `.ply` | 全 NUL 空壳 / `Intro for XXX` 占位 ⇒ **无正文，保留**（该缺就缺）|

## 六、验收清单（每层跑，缺一不可）

1. `assert len(out) == len(lines)`（行数/条目数不变）；
2. encode('gbk') 成功 + 无 BOM + CRLF（含裸 `\n` 者另验 LF/CRLF 计数）；
3. 汉字对真阳性（GB2312 判据）；
4. `.xscn` 独立解析器 `verify`：结构偏差 0；
5. 备份齐全 `backup\ORIGINAL-EFILE_*\`。
