# 57 · PeG 高分辨率 v6：面板左缘基准 620→844（刀具列绘制链一致性修正）

> 本档记录 2026-10-13 本轮：v5d 隔离实验的判读 →「画出来的刀具列」定位 → UI 绘制助手解剖 → v6a/v6b 的生成与站点表。
> 纪律：原版 `D:\Program Files\PeG\PeG030.exe` 绝不就地改；所有实验产物都是副本；实机试跑与截图一律由用户执行。

## 一、本轮要解决什么

v4/v5a 的右侧刀具列被**横向拉伸成 186 px 胶囊**（内容 x 800..985），而补过的按钮记录指向 986..1011 却什么都没画。本轮：
1. 用 v5d 隔离出「哪份数据影响点击区」；
2. 定位「真正被画出来的那一列」由哪份数据/哪段代码决定；
3. 据此造第一版**几何自洽**的产物 v6。

## 二、v5d 的判读（隔离实验，已由用户实机跑）

`PeG-1\PeG030-v5d.exe`（md5 `735a08d67a7cf95b4089d7f3678e62e6`，120 站点）＝ v5c **＋只把那 7 条按钮记录（`0x490494` 起，步长 36）的 `x`/`right` +224**。

|---|---|---|---|---|---|---|
| v3 / v5c / **v5d** | 762..787 | 762..787 | 762..787 | 762..787 | 762..787 | 762..787 |
| v4 / v5a | 800..985（拉伸） | 800..985 | 800..985 | 800..985 | 800..985 | 800..985 |

## 三、★「画出来的刀具列」= `0x4A21B0` 起的 12 条记录

```
{flags=0x1045, x=762, right=787, y=41/77/113/149/185/221/257/293/329/365/401/437, bottom=y+25}
地址：0x4A21B0 + n*0x24（n=0..11）        ← 字段 +2=x、+6=right
```
证据：
- v5c 截图实测的绘制方框在 shot y = 73/109/181/253/289/325/397/433，减去截图内容原点 y=31 得**内容 y = 42/78/150/222/…**，与该批记录的 `y` 逐条吻合；周期 36 与步长 0x24 一致。
- 字节核对：该批记录在 **v4/v5a/v6a 里 `x=986 / right=1011`**，在 **v5c/v5d 里仍 `762 / 787`**（v5d 只改了命中区那 7 条，没碰这 12 条）——与「v5d 画面与 v5c 相同」互为印证。

## 四、UI 绘制助手 `0x4235E5` 与两条调用路径

- `0x4235E5(rect_struct, ctrl_struct, index, dx, dy)`：先调 `0x47E0A0`，再按 `[[ebp+0xC]+4] + index*0x1C` 取控件尺寸，**dst = (rect.left + dx, rect.top + dy)**；并**要求 `rect.surface == [0x676904]`**，否则跳过。全 `.text` 有 **187 处**调用点。
- 四个 rect 结构（`0x676980` / `0x675540` / `0x686408` / `0x65A9B8`）都落在 `.data` 的 **BSS 段（VA ≥ ~0x4AF400，超出文件 raw `.data` 范围）** ⇒ **运行时构造，文件里没有初值**。这是「改文件里的记录搬不动界面」的结构性原因。
- **路径 A `0x41D0AC`**：矩形取 `[rec.x−2, rec.y, rec.right+6, rec.bottom]`，`dx = 0x26C − (rec.x−2)`、`dy = 0x16 − rec.y` ⇒ **最终 dst 恒为 (620, 22)**（把 dst 钉在面板左上角）；`ctrl=0x686408`、`index=0`。
- **路径 B `0x41D290`**：`index = +0x20`，dst = `(0x676980.left + rec.x, + rec.y)` ⇒ 真正决定「画在哪里」的是 **rect.left（运行时算出的面板左缘）**。

## 五、v6 的修法：4 处「面板左缘基准 620」

`work\peg\find_imm.py 0x26c`（全 `.text` 反汇编找立即数 620）**恰好命中 4 处**，全部是面板左缘语义：

| 名称 | 文件偏移 | VA | 指令 |
|---|---|---|---|
| panel-child | `0x01B967` | `0x41C567` | `sub ecx, 0x26c` |
| draw-widget | `0x01C51E` | `0x41D11E` | `mov eax, 0x26c`（`620 − 控件x`）|
| draw-rect-1 | `0x05F772` | `0x460372` | `push 0x26c` |
| draw-rect-2 | `0x0704A2` | `0x4710A2` | `mov eax, 0x26c`（`620 − 控件x`）|

全部 **620 → 844**（新面板左缘 = `1023 − 180 + 1`）：`6c 02 00 00` → `4c 03 00 00`。

⚠ 反向核对：**762 / 787 / 212 在 `.text` 里 0 命中** ⇒ 这些数字完全由数据区或运行时提供，代码里没有硬编码入口。

## 八、v6 实测结果：无变化（本实验设计有缺陷，已修正）

用户跑了 v6b（图1）与 v6a（图2）。`probe_btn.py` 六行实测：

| 版本 | y=86 | y=300 | y=420 |
|---|---|---|---|
| v5a | 800..813 / 879..885 / 900..910 / 972..985 | 800..813 / 836..948 / 972..985 | **800..985** |
| **v6a** | 与 v5a **逐段相同** | 与 v5a **逐段相同** | **800..985** |
| v6b | 与 v5b 同（y=300 少了 972..985 那段） | 800..813 / 836..898 | 800..985 |

⇒ **620→844 对刀具列毫无影响**。

**为什么这次实验等于空转（记录教训）**：绘制位置若为 `dst = 面板左缘 + (记录x − 基准)`，那么把 `面板左缘` 与 `基准` **同时** +224 是**恒等变换**（`844 + (986−844) = 620 + (986−620)`）⇒ v6a 必然与 v5a 逐像素相同。**改一处、留一处**才有信息量。

## 九、v7 二分实验（已生成，等用户跑）

已知：v5c（无 dx）干净；v4/v5a（全部 82 条 dx 记录）花屏；v5d（只组0）干净。⇒ 责任在其余 dx 记录组。

| v7b | 组4+组5（`0x4A2068` / `0x4A21B0`） | 邻居族（y=95,149,… 54 步长 / y=41,72,85,…） | `403e063abf8c521b6f79e3e0876044d5` |

**判读**：哪个变体让刀具列变成 800..985 的拉伸带，就锁定该组为「画面上那一列」的数据源。
