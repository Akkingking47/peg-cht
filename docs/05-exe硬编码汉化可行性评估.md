# OpenGen.exe 硬编码英文汉化 —— 可行性评估报告

- 对象：`D:\OpenPG2\OpenGen.exe`（6,316,032 字节，PE32，ImageBase 0x400000，product 26.03.30.0）
- 参考项目：**wicanr2/pg-cht** —— SSI《Panzer General / Allied General》Win95 版的 PE 二进制中文化工程
- 报告状态：**纯评估，未修改任何文件**
- 结论：**技术可行，且方法成熟有先例；但必须分阶段、带禁区清单推进**

---

## 一、结论摘要

| 问题 | 结论 |
|---|---|
| 能不能汉化 exe 内硬编码英文？ | **能**。字符串有唯一指针引用，可用「指针重导向」安全替换 |
| 有没有成熟先例？ | **有**。`pg-cht` 已用同类方法完整汉化 PG/AG 两个 EXE（AG 改了 13,321 字节） |
| 最大的坑是什么？ | ① 某串若同时用作 `strcmp` 查找键，改中文会破坏逻辑；② printf 格式符必须保留；③ 中文字节膨胀约 2 倍 |
| 需要重新编译吗？ | **不需要**。只改 4 字节立即数 + 往空闲区写数据，文件大小不变 |
| 建议？ | **先做 1～2 条纯显示串的 POC 验证**，确认后再分批推进；调试/日志串不值得翻 |

## 二、参考项目 `pg-cht` 的方法论（可直接借鉴）

它汉化了 `PG-cht.exe`（UI 230 条）与 `AG.EXE`（UI **499 条**），核心手法两条：

### 1. 原地翻译（仅「纯显示」串可用）
字符串只被显示、不被 `strcmp` 比对时，直接在原 slot 内替换。
**铁律**：`中文字节数 ≤ slot 容量 − 1`（留 NUL），Big5 下一个汉字 2 字节。

### 2. 指针重导向（本项目的关键方法）
当同一串**既用于显示、又作为查找键**时（直接改会抛 `未知错误 exTrue`）：

1. **保留英文原串**在原位（供 `.text` 内 `strcmp` 比对）
2. 在 `.data` 安全区**写中文副本**
3. **复制指针表**（英文版副本）
4. **修改原指针表**指向中文副本
5. 在 `.text` 的 **padding 区写新 getter 函数**
6. **bisection 定位「显示用 caller」**，只让显示路径走中文，其余 lookup caller 走英文

它明确列了**禁区**：战役名字串（同时是 strcmp key 与 SCN 文件名对应）、`SCENARIO.TDB` 等索引文件、`.text` 本体、文件路径串。

## 三、OpenGen.exe 结构实测

### 3.1 PE 节区

| 节区 | 文件偏移 | RVA | 大小 | 内容 |
|---|---|---|---|---|
| `.text` | `0x000400` – `0x477200` | `0x1000` | 4.6 MB | 代码 |
| `.rdata` | `0x477200` – `0x56FA00` | `0x478000` | 1.0 MB | 只读数据（**大量串在此**）|
| `.data` | `0x56FA00` – `0x5BEC00` | `0x571000` | 324 KB | 可写数据（**部分串在此**）|
| `.rsrc` | `0x5BEC00` – `0x606000` | `0xEAB000` | 297 KB | 资源（ICON/BITMAP/DIALOG/STRING/MANIFEST…）|

**VA 换算**：`VA = ImageBase(0x400000) + 节区RVA + (文件偏移 − 节区文件偏移)`

> ⚠️ 注意：我最初算指针时漏加 ImageBase，导致「指针命中 0 处」的假结论。加上后每个串都精确命中 1 处。

### 3.2 字符串存储形态

字符串以 **NUL 分隔、紧密排列、无 padding**。例：

```
FO=0x4EE070  [345 字节]  Welcome to Open General \n\nBe sure you read "Read Me First.htm"...
FO=0x4EE1D0  [301 字节]  Welcome to Open General \n\nAfter closing this window you can review...
FO=0x4EE350  [249 字节]  Click left menu icon to enter equipment's browser to select any...
```

**后空隙 = 0**（紧邻下一条串）→ **中文必然溢出 → 原地替换不可行，必须指针重导向**。

### 3.3 引用形态（关键可行性证据）

反汇编证实：引用形式统一为 **`68 <VA32>`（`push imm32`，5 字节指令）**，且**每串只有一处**：

```
0x2D1E10:  68 70 EE 8E 00   push 0x8EEE70    ← "Welcome to Open General..." 长文本
0x2D1E3E:  68 D0 EF 8E 00   push 0x8EEFD0    ← 第二段 Welcome
0x3FA0C4:  68 5C FF 90 00   push 0x90FF5C    ← "Do you really want to exit"
0x2D1F3D:  68 50 F1 8E 00   push 0x8EF150    ← "Click left menu icon..."
```

**全量统计**（`.text` 内 `push imm32` 指向 exe 镜像共 **19,108 条**指令、**10,974 个唯一目标**）：

| 串的引用形态（≥8 字节英文串） | 条数 | 字节数 | 汉化风险 |
|---|---|---|---|
| **唯一 push 引用** | **3,941** | 97,717 | **低，优先做** |
| 多处 push 引用 | 403 | 8,320 | 中，需逐个确认有无 lookup |
| 无 push 引用（指针表/其他） | 5,815 | 145,207 | 高，暂缓 |

### 3.4 可用空闲空间

`.data`/`.rdata` 内**连续 NUL ≥ 32 字节的空隙共 636 处**，最大 559 字节（`FO=0x570AC9`），另有大量 253 字节块 —— 足够安放中文副本。

### 3.5 玩家可见 UI 的分布

| 区域 | 范围 | 内容 |
|---|---|---|
| **战役浏览器区** | `0x4EE000` – `0x4EF000` | `Welcome to Open General` ×2、`Click left menu icon...`、`Do you want to play the tutorial now?` 等长文本（约 10 条） |
| **UI/调试区** | `0x4F0000` – `0x520000` | `All nations`/`All equipments`/`All authors`/`All periods`、`Campaign file not found`、`Do you really want to exit`、`Cancel`/`Yes`/`Warning`/`Are you sure`、文件对话框过滤器等 |

同时该区域混有**大量调试/日志串**（`>>> Checking advance for U:%d`、`ExpectFire`、`KillFrac`、`Ent:%d`），**这些不显示给玩家，无汉化价值**。

## 四、拟定技术方案（指针重导向）

对每一条待汉化串：

1. **备份** `OpenGen.exe` → `OpenGen.exe.bak`（并在 `backup\` 镜像一份）
2. **翻译**该串（保留所有 `%d`/`%s`/`\n` 等格式与转义）
3. **分配空隙**：在 `.data` 空闲区找出足够大的连续 NUL 块
4. **写入中文副本**：GBK 编码 + NUL 结尾（`中文字节数 ≤ 空隙大小`）
5. **改写引用**：把 `.text` 中该串的 `push imm32` 立即数改成中文副本的 VA（**只改 4 字节，指令长度不变**）
6. **校验**：文件大小不变、PE 校验和与节区表未破坏、GBK 解码回读正确
7. **实测**：启动游戏确认该处显示中文且功能正常

**回滚**：直接用 `.bak` 覆盖即可，无需逆向。

## 五、风险清单

| # | 风险 | 说明 | 对策 |
|---|---|---|---|
| R1 | **字符串兼作查找键** | 若该串被 `strcmp` 用于匹配（战役名、efile 名、文件名），改中文会导致匹配失败、报错或崩溃 | **仅汉化「唯一 push 引用」且语义为纯显示的串**；对可疑项先做 `pg-cht` 式 caller bisection |
| R2 | **printf 格式符** | 1,502 条串含 `%d`/`%s` 等，误改会导致崩溃或输出错乱 | 翻译时**逐字保留**格式符；改后统计格式符数量必须一致 |
| R3 | **中文字节膨胀** | GBK 2 字节/汉字，长串可膨胀至 2 倍 | 一律走空隙区，**绝不原地替换**；写入前校验 `≤ 空隙大小` |
| R4 | **空隙被占用/重叠** | 多个串共用空隙会互相覆盖 | 维护**空隙分配台账**，用完标记；每次写入前后校验 |
| R5 | **长度限制** | 某些串显示区有固定像素宽度（如按钮），过长会溢出/截断 | 参考已完成的 `strings-zh.txt` 经验，**译文尽量短**；按钮类按原宽度的 1.2 倍内控制 |
| R6 | **多显示器/DPI** | 与本次 exe 修改无关，但中文变长会加剧布局问题 | 实测每个改动点 |
| R7 | **版本漂移** | 官方更新 exe 后偏移全变 | 在报告中**记录 exe 指纹**（大小 + 关键串偏移），换版本必须重新扫描 |

### 明确的禁区（绝不修改）

1. **文件路径串**：`%sSCENARIO\%s.buy`、`README\Read Me First.htm`、`OpenIntro.avi`、`efile_ag\` 等
2. **printf 格式符本身**（`%d`/`%s`/`%-2d` 等）
3. **`settings.cfg` 的键名**（`UI_Lang`、`Font1`、`EFolder`…）
4. **疑似 strcmp key**：战役名/场景名/efile 名（需先验证）
5. **`.text` 代码本体**（除经确认的 `push` 立即数外一律不动）
6. **调试/日志串**（无收益，徒增风险）

## 六、工作量与分阶段建议

### 分阶段路线

| 阶段 | 范围 | 条数（估） | 说明 |
|---|---|---|---|
| **P0 可行性 POC** | `Do you really want to exit ? ...` 1 条 | 1 | 验证「写副本 + 改 push」全流程与实测效果，**做完就可判定走不走这条路** |
| **P1 战役浏览器** | `0x4EE000`–`0x4EF000` 长文本 | ~10 | 收益最直观（玩家一启动就看到） |

### 与现有工作的关系

- 本次已完成的 `strings-zh.txt`（UI 775 条）**不受影响**，两者互不冲突
- exe 汉化补的是**盲区**：战役浏览器、程序级对话框（`strings` 机制覆盖不到的部分）
- 若做 exe 汉化，**应先确保 `strings-zh.txt` 已是最新**，避免重复劳动

1. **空隙总量够不够**：需统计 `.data`+`.rdata` 内 ≥64 字节空隙的**总字节数**（上次遍历超时，未取全）

5. **与 efile 的 `TEXT-ZH` 是否有交互**：确认 exe 内是否有影响 `TEXT-ZH` 加载逻辑的字符串

## 八、结论

**这条路走得通，而且比想象中简单** —— 因为 OpenGen 的硬编码串**每一条只有一处 `push` 引用**，修改只涉及 4 字节立即数，不需要像 `pg-cht` 那样大规模做 caller bisection（那是 PG/AG 用指针表索引时才需要）。

真正的风险不在「改不进去」，而在 **`R1 字符串兼作查找键`** 与 **`R2 格式符`** 这两项——它们决定「哪些能改」。

**建议**：先做 **P0（1 条串的 POC）**。如果 POC 通过，再按 P1→P2→P3 分批推进；每批完成后立即实测 + 备份，保持可回滚。

本报告未修改任何文件；`OpenGen.exe` 与游戏目录保持原样。
