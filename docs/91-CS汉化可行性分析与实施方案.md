## 一、可行性结论

### 1.1 总判定

**技术可行，且关键障碍比预期小：当前无需修改字体调用、无需自造字库。**

三条决定性实测结果：

| # | 结论 | 证据 |
|---|---|---|
| 1 | 引擎全部文本走 **ANSI（A 版）GDI API**，按**系统 ANSI 代码页**解释字节 | `ef.exe` 只导入 `TextOutA / ExtTextOutA / DrawTextA / DrawTextExA / CreateFontA / GetTextExtentPoint32A`，**无任何 `*W` 宽字符版** [实测] |
| 2 | 本机 **ACP = 936**，因此 ANSI 路径天然按 **GBK** 解释 | 注册表 `Ncp\CodePage\ACP=936`，`GetACP()=936`，culture `zh-CN` [实测] |
| 3 | 引擎硬编码的 3 个英文字体名 + `charset=0(ANSI_CHARSET)`，在 ACP=936 下**会被 GDI 自动替换成中文宋体并正确渲染汉字** | 用与 `ef.exe` **完全相同的 `CreateFontA` 参数**做独立渲染实验：`Times New Roman` / `Times Roman` / `MS Sans Serif` × 高度 10/14/18/24，GBK 字串「装甲师」「第1装甲师」全部正确成字，宽 17 px/字（h=18）[实测，图见 `work\jtcs\view\p_*.png`] |

也就是说：**只要系统区域是中文（936），把文本换成 GBK 字节即可显示中文**。字体补丁从"必需项"降级为"备用项"（见 §2.3）。

### 1.2 落地仍需同时满足的四个条件

1. **运行环境固定 cp936**：中文 Windows，或用 Locale Emulator 强制。当前机器已满足；若在有日文/英文区域的机器上跑，会整体乱码（这是纯环境问题，非代码问题）。
2. **文本改写必须整层彻底**：文件里现存的 `cp1252` 变音字节（`ä ö ü é ë ° " "`）必须一次性归一化，**不能"译一半留一半"**，否则 0xE4/0xF6 之类会被当 GBK 首字节吞掉下一个字符（§2.4 第 3 条）。
3. **含字位图重绘**：主菜单等 5+ 张 8bpp 位图把英文"烧"在像素里，必须重画（§2.2 L8）。
4. **翻译产能**：East Front 待译正文约 **28.7 M 字符**（org 16.7M + oob 9.7M + txt 2.3M），是纯工作量问题，不是技术问题。必须分期（§4），不可一次到底。

### 1.3 明确的不可行/高成本盲区

| 项 | 判定 |
|---|---|
| 帮助文件 `*.HLP`（7 个，1999 年 WinHelp 格式） | 无法在无源码情况下编辑正文；只能①保留英文 ②另出中文 PDF/CHM ③用 HC 反编译重编（高风险、低收益）→ **建议不做** |
| 声音/过场（`.ogg` 299 个、`MatrixIntro.avi`） | 语音为英文/音效，不属文本层；不做 |
| 中文输入（改名、聊天、邮件） | 引擎用 ANSI 编辑框 + 中文 IME 理论可用，但 `WM_CHAR` 双字节处理未验证 **[推定：可能丢半个汉字]** → MVP 顺带测一次 |
| 手写/艺术字标题（主菜单 "MENU"/"MAIN MENU" 立体字） | 属位图，需美术重绘，非脚本可解 |

### 1.4 关于"世纪雷神曾发行完全汉化版"这条线索

**线索核验**：孔夫子旧书网在售实物「游戏光盘 **欧洲战火 东线风云** 简体中文版（**世纪雷神**，内含一张 CD、说明手册、游戏介绍）」（`book.kongfz.com/204914/10207693660`）。这说明 1998–2000 年代确有简体中文零售版存在，**但它是二手书商的商品描述，不是技术文档**。

**它对技术可行性的参考价值（旁证，非验证）**：

- 正面：若当年真做到了界面+剧本全中文，说明**该引擎在中文 Windows 下确实能显示中文**，与本次 §1.1 的实测方向一致；也说明"不改渲染核心、只换文本+字体环境"这条路当年走得通。
- 具体可借鉴的疑点（值得在拿到实物后核对）：他们**有没有改字体名**（决定我们是否需要备用补丁）、**位图怎么重画**（主菜单/Turn 框/F2 框）、**`.org` 单位名是否全译**（决定工作量口径）。

**不能视为已验证事实**：无版本号（1999 年 1.x 与当前 2.05 的 exe 完全不是同一构建：旧版为 Borland OWL 链，2.05 为重编译的 MFC9）、无"完全"的客观标准（卖家措辞）、未见截图以外的技术信息。

**可进一步核实的遗留资源**（按性价比排序）：
1. 孔网/闲鱼实物 CD → 提取其中 `*.scn/.org/.oob` 中文文本 → 直接成为**翻译记忆（TM）**，可省 50–70% 翻译量；同时提取其 `ef.exe` 做**字体方案对照**（看是否改了 facename）。
2. Internet Archive / 老光盘镜像站检索 "欧洲战火 东线风云"、"Campaign Series 中文版"。
3. 中文老论坛（战争艺术、铁血、游侠、3DM 早期版块）的"东线风云 汉化补丁"帖 → 若存在独立汉化包，其文件清单可直接复用为**待译清单**。
4. Matrix 官方论坛 Campaign Series 版块搜 "Chinese / localization / DBCS" → 确认官方是否曾考虑本地化（决定后续升级是否会覆盖我们的补丁）。

## 二、主要障碍与证据

### 2.1 目录结构与三部作品的资源关系

```
John Tiller's Campaign Series\            ← 共享层
├─ East Front\   West Front\   Rising Sun\      三作各自独立的数据+图形集合
├─ Mods\  User_Mods\        ← JSGME 模组目录（Mods/<模组名>/<游戏目录>/<文件> 镜像结构）
├─ Tools\ (JSGME, JTCS_Unitviewer, ScnPick)      Manuals\  AutoPlay\  redist\
├─ campres.exe(2.4MB, 战役资源工具)  JTCSUpdate.exe  RegSetup.exe  autorun.exe
└─ 8 个 *.jsgme（模组说明戳）
```

**三部作品是同一引擎的三个数据包**，不是三个独立程序：

| 项 | East Front | West Front | Rising Sun |
|---|---|---|---|
| 主引擎 | `ef.exe` **1,609,488 B** | `wf.exe` **1,610,000 B** | `risun.exe` **1,610,000 B** |
| 资源条目 | 107 | 107（同构） | 107（同构） |
| MENU / DIALOG / STRING 块 | 1 / 36 / 30 | 1 / 36 / 30 | 1 / 36 / 30 |
| 唯一 ASCII 串 | 4,446 | 4,311 | 4,297 |
| 编译器 | MFC 9.0 / MSVC2008（`mfc90.dll`,`MSVCP90.dll`,`MSVCR90.dll`） | 同 | 同 |

`Rising Sun` 的引擎**改名 `risun.exe`**（2.05 changelog：与 NVIDIA 命名空间冲突导致地图扭曲）——所有打补丁脚本必须按"按目录取 exe 名"而不是硬编码 `ef.exe`。

三作 exe 字符串重合度：EF∩WF **2,820（EF 占 63.4%）**、EF∩RS **2,827（63.6%）**、三作共有 **2,776** [实测]。→ **译好 EF 等于译好另外两作六成引擎文本**。

目录里还留着 `OWL253.DLL / MFC42.DLL / BC453RTL.DLL / BIDS47.DLL / MSVCRT.DLL`，但 `ef.exe` **并不导入**它们（导入表只有 11 个 DLL）→ 1998 年 Borland OWL 时代的残留 [实测]。

### 2.3 字体与双字节渲染（East Front 专项）

**实测到的全部字体调用**（`ef.exe` 21 处 `CreateFontA`，经三层封装 `0x4D23C0 → 0x4D2970`）[实测]：

| 字体名（`.rdata` 字面量） | 高度（px） | 字重 | charset |
|---|---|---|---|
| `Times New Roman` | 18 / 16 / 14 / 20 | 700 / 0 | **0 = ANSI_CHARSET** |
| `Times Roman` | 10 / 14 / 18 / 24 | 700 | **0** |
| `MS Sans Serif` | 14 / 12 / 24 / 16 | 400 / 700 / 0 | **0** |

即：**没有 `DEFAULT_CHARSET`，没有 GB2312_CHARSET，也没有自定义点阵引擎**。

**独立渲染实验（不动游戏，本进程内建内存 DC）结果**：

| 配置 | GBK「装甲师」 | 结论 |
|---|---|---|
| `Times New Roman`, h=18, charset=0 | 51 px 宽、17 px 高，正确成字（宋体风格） | ✅ 自动替换 |
| `Times New Roman`, h=14 | 39 px，正确 | ✅ |
| `MS Sans Serif`, h=14 / 12 / 10 | **恒为 39 px 宽、13 px 高**（三种高度结果相同） | ✅ 能显示，但走的是**点阵替换**，请求高度被忽略 |
| `times Roman`, h=10 | 27 px（9 px/字） | ✅ 小字号可用 |

**推论**：
1. **不需要改字体名**（ACP=936 时 GDI 已按 `ANSI_CHARSET → GB2312` 完成替换）。
2. **字号 ≥12 px 处中文清晰；10 px 处偏挤但可读**。引擎实际用 14/16/18/20/24 为主 → 观感无问题。
3. `MS Sans Serif` 请求 10 px 却给 13 px 点阵 → 少数小字区域（如 Turn 计数）可能**比原文略高**，属**布局风险**而非乱码。
4. 若实测出现方框/空白（某些系统缺宋体或 GDI 替换策略不同），**备用方案**：把 `.rdata` 里 3 个字面量就地改成 `SimSun`（13→6 字节，等长可行、零风险）→ 已在实验中验证 `SimSun + charset=0` 同样正确。

**仍需运行验证的一点**：引擎是**整串一次 `ExtTextOutA`** 还是**逐字节循环**。已确认文本输出被抽象成 14 方法虚表、`TextOutA/ExtTextOutA` 封装都带**显式字节长度**参数，且唯一可见的调用方传的是 `strlen()` 结果 → **倾向整串绘制，DBCS 安全 [推定]**；但虚表另有实现，无法静态排除某处逐字节绘制。MVP 专门测这一条（§3）。

### 2.4 编码陷阱（本项目最容易翻车的地方）

1. **文本文件不是纯 ASCII**：`ä(0xE4) ö(0xF6) ü(0xFC) é(0xE9) ë(0xEB) °(0xB0) "(0x93) "(0x94)` 真实存在。分布：EF 的 76 个 `.org`、32 个 `.oob`、13 个 `.scn`、3 个 `.txt`（`unittext.txt` 380 字节、`mapname6.txt` 69 字节，`SOMUA-Kégress`、`Citroën`、`Saadjärv` 之类）。WF 更多（`.oob` 1,310 字节）。
2. 这些字节在 **GBK 语境下是"首字节"**：`0xE4 0x67`（`ä`+`g`）会被读成**一个**汉字。所以**混写 = 花屏 + 吞字**，必须先 `decode(cp1252)` 归一化再 `encode(gbk)`。
3. `0x93/0x94`（弯引号）同样危险，且它们出现在 `KV-1e ("ekranirovaniy")` 这类正文里 → 建议统一改成中文引号或 ASCII 引号。
4. **换行必须保持 CRLF**；**GBK 输出禁止 BOM**；编号行（如 `.scn` 第 1 行的 `12`、`.scl` 第 8/9 行的文件名引用行）**一律不动**。
5. `.scn/.scl` 第 8、9 行是**被 ±1 偏移"加密"过的文件名引用**（`//Fnqjh-l`o` → `00Gorki.map`，不同文件偏移方向还不一样）。它不参与显示，**保持原样**，不要试图"修好"。

## 三、最小可行验证方案（MVP）

> 目的：用 **≤6 个文件、≤2 小时**，一次性回答 4 个未知数：①GBK 是否显示 ②是否逐字节绘制 ③数据文件中文是否被接受 ④位图重绘是否可行。
> **前置：不做备份不动手。** 本机已有 JSGME，建议直接用模组方式做（可一键还原）。

### 3.1 备份（第一步，不可跳过）

```bat
:: ① 原始基线（只读留档，放工作区，不进游戏目录）
robocopy "D:\Program Files\John Tiller's Campaign Series\East Front" ^
         "D:\DSH\军事游戏汉化\backup\jtcs-ef-orig-20261020" /E /NFL /NDL
:: ② 记录 md5，后续任何一步都可核对是否被污染
certutil -hashfile "…\East Front\ef.exe" MD5
```
JSGME 方式：`Mods\ZZ-CN-MVP\` 下新建 `East Front\`，把要改的文件**副本**放进去，启用即覆盖、停用即还原（JSGME 自动把原件搬到 `Mods\!BACKUP\`）。

| **T4** | L8 位图 | `phasebox.bmp` 的 `Axis Player` → `轴心玩家` | GIMP 抹掉原字→宋体 16 px→加同色描边→**保持 277×298、调色板索引不变** | 回合框在游戏内显示中文，无锯齿错位，与"Turn  x of y"数字不打架 |

**T2 的替代触发点**（若一时打不出该提示）：任选一条状态栏/消息框短串，如 `Locations...`（若为资源则不行，须选 `.rdata` 里的引擎串）。挑选原则：**整串唯一、长度 ≥10、易于在游戏里触发**。

### 3.3 成功判定标准（全过 = 技术路线成立）

- [ ] 4 个测试点均**显示中文且无乱码**；
- [ ] 游戏**能正常启动、能进场景、能退回合**（无崩溃、无存档报错）；
- [ ] 除被改的 4 处外，**其余界面文字与原文逐字一致**（证明没有连带破坏）；
- [ ] `ef.exe` 大小**不变**（等长替换的副产品，用于快速判断有没有误写）；
- [ ] 关掉游戏后，**没有新增/损坏文件**（除预期的那几个）。

### 3.4 失败回滚（每种失败都有确定动作）

| 现象 | 首选动作 |
|---|---|
| 任一测试导致崩溃/黑屏 | JSGME「Disable」→ 或从 `backup\jtcs-ef-orig-20261020` 拷回 4 个文件 → 复核 md5 |
| `ef.exe` 打不开（资源重建把 PE 改坏） | 直接回滚 `ef.exe`；改用"只改 `.rsrc` 内的 UTF-16 串、不重建节表"的自写脚本 |
| 中文显示为方块/空白 | 先确认 ACP=936；仍不行 → 启用**备用字体补丁**（`Times New Roman→SimSun` 等 3 处，等长替换）重测 T2 |
| 中文显示为 `ÖÐÎÄ` 式拉丁乱码 | 说明写入的不是 GBK（大概率存成了 UTF-8）→ 检查编码后重写 |
| 显示一半/隔字/只出奇数位 | **逐字节绘制**，见 §3.5 分支 B |

### 3.5 决策条件（MVP 之后怎么走）

- **分支 A（T1–T4 全过）** → 按 §4 全量推进，优先级 L1 → L3/L5 → L4 → L6 → L2 → L8。
- **分支 B（只有 T2 失败：隔字/半字）** → 引擎存在逐字节绘制路径。对策按成本排序：①**放弃引擎内文本**，只做 L1+L3+L4+L5+L6+L8（游戏内 80% 可读文本在数据层，界面按钮仍是英文）；②定位逐字节绘制函数（虚表 14 方法逐个下断）改为 `IsDBCSLeadByte` 跳过一字节——**属改程序，需用户明确授权**。
- **分支 C（T2 过、T3 失败：中文名导致脚本异常）** → 场景名保持英文，只译简报正文；`.org` 名称同理。
- **分支 D（T4 只能做到难看但可读）** → 位图重绘降级为"二期"，先交付文本层。

## 四、East Front 详细实施方案（分阶段）

> 总原则：**原文零覆盖**（全部走 `Mods\ZZ-CN-EF\` 的 JSGME 模组 + 工作区副本）、**译法与逻辑分离**（`*.tsv` 对照表 + 生成脚本）、**每步可回读校验**。

### 阶段 0 · 基线与工具（0.5 天）

| 项 | 内容 |
|---|---|
| 输入 | 原版安装目录 |
| 动作 | ① 全目录 md5 清单 → `baseline\ef.md5`；② 建 JSGME 模组骨架 `Mods\ZZ-CN-EF\East Front\`；③ 固化 4 个工具（见 §6.1）；④ 用 `res_dump.py`/`strings_probe.py` 导出 EF 全部原文到 `work\jtcs\src\` |

### 阶段 1 · 文本清单与对照表（2–3 天）

统一对照表格式（TSV，UTF-8 BOM，给译者和脚本共用）：

```
id  layer  file  locator            en                      zh   max_bytes status
L2-0001 rdata ef.exe 0x000E8A2C     Fixed units cannot assault  固定单位不能突击  27  done
L3-0123 scn 00Gorki.scn L2          The Hard Fought Lesson  苦战的一课        42  done
```

- `locator` 对 L2 用**文件偏移**（唯一、可复算）；对文本层用**文件名+行号+列号**。
- `max_bytes` 由脚本自动测（L2 必填，L3/L4 为软限）。
- `status`：`todo / done / keep(不译) / hold(待定)`。

**先出一份"不译清单"**，否则永远做不完：单位型号（`PzKpfw IV`、`T-34/85`）、番号（`1. Panzer Division` 建议译"第1装甲师"，但 `PzKpfw` 系列不译）、人名（将领译名 vs 保留原文，建议译+括注）、`$()` 宏（`$(1-70)`）、`.scn` 编号行、`.scl` 第 8/9 行、`*.pdt/dat` 数字。

### 阶段 2 · 术语与文风（1 天，可并行）

- 建 `glossary\cs-glossary.tsv`（三作共用，约 800–1,200 条）：
  - 军事名词用军语：`Assault→突击`、`Opportunity Fire→机会射击`、`Hexside→六角格边`、`Line of Sight→通视/视线`、`Fatigue→疲劳`、`Morale→士气`、`Command Range→指挥半径`、`Victory Points→胜利点数`、`Replacement→补充兵员`。
  - 机制词玩家化：`Load/Unload→装载/卸载`、`Digging-In→构筑工事`、`Double Time→强行军`。
  - 地名按国家规范（`Taiwan`→`中国台湾` 之类一律按规范）。
  - 单位名：`第N装甲师 / 第N步兵师 / 第N军 / 集团军群`，罗马数字番号保留或转阿拉伯数字**全项目统一**。
- 复用本工作区既有资产：`glossary\` 下的 OpenPG/PeG 词库可直接对表复用（同题材、同二战装备体系）。

### 阶段 3 · 分层回写（按"性价比/风险"排序）

| 序号 | 层 | 工具 | 输入 | 输出 | 验证 |
|---|---|---|---|---|---|
| 3.1 | **L1 资源** | Resource Hacker（人工）+ `rsrc_rebuild.py`（脚本化批量） | `.tsv` 中 L1 段 | 改好的 `ef.exe` 副本 | 回读资源：字符串表 173 条逐条比对；菜单 165 项计数一致；`ef.exe` 能启动 |
| 3.2 | **L3 场景** | `apply_scn.py` | `scn.tsv` | 258 `.scn` + 166 `.scl` 副本 | ①行数不变 ②数字行逐字节一致 ③简报**重折行后行数 ≤ 原行数**（若超出，优先缩句而非超框）④抽样 10 个进游戏看简报 |
| 3.3 | **L5 txt** | `apply_txt.py` | `txt.tsv` | 11 个 txt | 首列键逐行对齐；字符数变化报告 |
| 3.4 | **L4 编成** | `apply_org.py`（列解析，仅替换末列） | `org.tsv`/`oob.tsv` | 405 个文件 | ①前导空格数逐一相同 ②ID 列 md5 相同 ③随机抽 3 个 `.org` 进游戏看单位面板 |

**L2 的三条硬规则**：①先在 `.rdata` 里按**精确 C 串**定位（前后都是 `\0` 才算命中，避免命中子串）；②替换后必须**重新扫描一次**确认没有残留旧串；③同一英文串出现多处时**全部替换或全部保留**，不能只改一处（否则同一提示两种语言）。

### 阶段 4 · 编码治理（贯穿，但要有独立验收）

- 统一流水线：`read → decode(cp1252) → 归一化变音（ä→ae / é→e / “”→" / °→度）→ 翻译 → encode(gbk) → 写回（CRLF, 无 BOM）`。
- 归一化表要落盘（`normalize.tsv`），不靠临场判断。
- **验收脚本 `check_encoding.py`**：对每个输出文件做 ①GBK 可解码 ②无孤立首字节 ③无 BOM ④CRLF 计数与原文件相同 ⑤非 ASCII 字节全部落在 GB2312 区或为显式白名单。

| # | 用例 | 关注点 |

| 2 | 选场景（列表滚动、按国家/年份筛） | 中文场景名是否截断、排序是否异常 |
| 3 | 进场景 → 顶部状态栏/地形名/回合框 | **T2 同类**：引擎绘制串是否完整 |
