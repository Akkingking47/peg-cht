## 一、v4 取证后的推论

v4（`PeG-1\PeG030res.exe`，md5 `2107b73bbfd4213719b622a1a9d4c6ad`）实机截图的结论（见 55 号档）：

- **地图有效**：内容区 x 888..1016 是地形，地图铺满到 ~1016 ⇒ 用户目标「一屏看得更多」在 v4 上成立。
- **界面无效**：右侧工具列在 v3 位于内容 x 762..787（26 px 方块 + 清晰图标），v4 变成内容 x 800..985（**186 px 横向拉伸胶囊**）；
  而 v4 补过的按钮记录指向的是 986..1011，那里**什么都没画**（是地形）。
- **底栏没动**：v4 已给底部状态条记录 y/bottom +168，画面里它仍在原位置。

⇒ 推论：**界面控件的位置不是直接取自 `.data` 记录，而是运行时在代码里重算的**；
v4 只改了数据（163 处 `x += 224`）和 `.text` 里的一部分常量，没碰那条重算链。

## 二、代码链（本推论的一手证据）

面板矩形（VA 0x41C4A6 起）：

```
0x41C4CD  mov dword ptr [ebp-0x10], 0x16     ; 22 = 顶栏高
0x41C4D4  mov dword ptr [ebp-8],   0x23B     ; 571  ← v4 未改
0x41C4DB  mov dword ptr [ebp-0xC], 0x31F     ; 799  ← v4 未改
0x41C4EB  mov word ptr [ebp-0x18], 0xB4      ; 180 = 面板宽
0x41C502  movsx edx,[ebp-0x18]; mov eax,[ebp-0xC]; sub eax,edx; add eax,1
          ; left = right - 180 + 1 = 620
0x41C511  push 0; push 0; push 0; push 0x686408; lea ecx,[ebp-0x14]; push ecx
0x41C520  call 0x4235E5                      ; 画面板底 {620,22,799,571}
```

面板内子控件循环（同一函数，紧随其后）：

```
0x41C528  mov word ptr [ebp-0x1C], 0x20      ; i = 0x20
   …      imul ecx,ecx,0x24 / movsx edx,[ecx+0x490474]   ; 记录 y
          sub   edx, dword ptr [ebp-0x10]                ; y - 22
          imul eax,eax,0x24 / movsx ecx,[eax+0x490472]   ; 记录 x
          sub   ecx, 0x26C                               ; x - 620（面板左缘）
0x41C575  call 0x425407                       ; (面板结构, 索引, x-620, y-22)
   …      cmp eax, 0x27 ; 循环到 0x27（共 8 个子控件）
```

屏幕边框（VA 0x44C5B8 起，两次调用同一个绘制助手 0x4235E5）：

```
0x44C5CC  push 0x23A   ; 570  ← v4 未改（.rdata 里的同值常量 v4 改过，这条没有）
0x44C5D1  push 0x31C   ; 796  ← v4 未改
```

视口裁剪三组（每组结构相同：`cmp → jle → mov reg,imm → sub reg,[滚动量] → mov [Blt矩形字段],reg → mov [限值],新值`）：

```
0x44C730  mov eax, 0x320   ; 800  ← v4 未改（同组 cmp 与限值 v4 已改 1024）
0x44C777  mov edx, 0x258   ; 600  ← v4 未改
0x44C869  mov edx, 0x320   ; 800  ← v4 未改（第二份拷贝）
0x44C8B0  mov ecx, 0x258   ; 600  ← v4 未改
0x44CC67  mov edx, 0x320   ; 800  ← v4 未改（第三份拷贝）
0x44CCAE  mov ecx, 0x258   ; 600  ← v4 未改
```

⇒ 同一个基本块里「`cmp` 说的是 1024、参与运算的 `mov` 还是 800」= 自相矛盾，
这正是 v3/v4 右侧与底侧那块区域从未被写入（显示未初始化表面 = 品红/绿条 + 黑块）的原因。

## 四、实机试跑怎么读结果（建议 v5c 优先）

1. **右侧工具列**：方块是否回到「26 px 方块 + 清晰图标」（而不是拉伸胶囊）？位置是否贴着右边（内容 x≈986..1011）？

对照预期：

- 若 **v5c** 右侧方块贴合右缘且可点、底栏就位 ⇒ 「代码驱动布局」假设成立，v5c 即正确架构，后续只做图标/细节。

### 三条结论

1. **工具列的横向拉伸由那 14 个字段（7 条按钮记录的 `x`/`right`）直接造成**：
   v4 位移了它们 ⇒ 800..985 的 186 px 拉伸带；v5c 不位移 ⇒ 与 v3 完全一致。
   最可能的机制是 pg-cht 记的「**dst/src 共用同一条 RECT**」陷阱：记录既是目标框又被当源框用，
   一改就变成「从越界的源拉伸到目标」，于是出现 800..985 这种怪几何。
2. **面板/边框/裁剪那 10 处代码立即数对工具列毫无影响**（v5a 与 v4 同型）；v5b 反而更差 ⇒
   它们属于别的界面元素（面板底、屏幕边框、地图视口裁剪），不是工具列的绘制源。
3. **底栏不是记录驱动的**：字节核对确认 v4 确实把 `0x4A24F0` 记录改成了 `y=744 / right=1014`
   （`20 18 0A 00 E8 02 F6 03 FA 02`），但画面里底栏仍在原位（内容 y≈569..587、x≈84..702，
   与任何记录都不吻合）⇒ 底栏由另一条代码路径绘制，靠改记录让底栏下移行不通。
