## 一、本轮要解决什么

v5c 是目前最佳基线（地图铺满 1024，界面元件形状与原版一致）。**唯一大缺口**：右侧刀具列仍停在
原 x（内容 762..787），而把它的记录 x/right +224 之后并不是「平移」，而是从 800 起被**横向拉伸**。
本轮就是找出这条绘制公式，从而知道「该改哪个数」。

## 三、★ 绘制公式（handler `0x44ACDA` 反汇编，静态度量）

```
0x44ACDA  handler(index)
  movsx eax,[ebp+8] ; 越界检查 (0 <= index < [0x4af460])
  0x44AD00  imul eax,eax,0x24
  0x44AD03  mov  ecx,[0x4cce2c]        ; 当前控件数组指针
  0x44AD09  add  ecx,eax               ; rec = [0x4cce2c] + index*0x24
  0x44AD11  movsx eax,[edx+2] -> [ebp-0x18]   ; rect.x     = rec.x
  0x44AD1B  movsx edx,[ecx+4] ; sub edx,1 -> [ebp-0x14]  ; rect.y     = rec.y - 1
  0x44AD28  movsx ecx,[eax+6] ; add ecx,1 -> [ebp-0x10]  ; rect.right = rec.right + 1
  0x44AD35  movsx eax,[edx+8] ; add eax,1 -> [ebp-0x0c]  ; rect.bottom= rec.bottom + 1
  0x44AD3F  mov  ecx,[0x676904] -> [ebp-8]   ; rect.surface（主表面）
  ...
  0x44AD75  mov  ecx, 0x16(22) ; sub ecx,[ebp-0x14]  ; dy = 22 - (rec.y-1) = 23 - rec.y
  0x44AD7E  mov  edx, 0x2EF(751) ; sub edx,[ebp-0x18] ; dx = 751 - rec.x
  0x44AD86  push edx ; push 1 ; push 0x663410 ; lea eax,[ebp-0x18] ; push eax
  0x44AD92  call 0x4235E5        ; 5 参数：rect*, ctrl=0x663410, mode=1, dx, dy
  （另一分支 0x44AD9C/0x44ADA5 同型，只是多压一个 dy）
```

⇒ **绘制位置不是直接用记录坐标，而是用「锚点 − 记录坐标」算出的相对量**：
`dx = 751 − rec.x`、`dy = 22 − (rec.y − 1)`。

母本里 `rec.x = 762` ⇒ `dx = 751 − 762 = −11`（很小的相对偏移）。
v4 / v7a 把 `rec.x` 改成 986 而锚点仍是 751 ⇒ `dx = −235`，量级完全不同 ⇒
助手 `0x4235E5` 拿着一个越界/离谱的相对偏移去取样并贴图 ⇒ **就是那条 186 px 拉伸带的来源**。

## 十、绘制链全图（本轮静态度量，已确证部分）

```
handler 0x44ACDA(index)
  rec = [0x4cce2c] + index*0x24            ; 当前控件数组（setter 0x43FE70）
  rect = { x=rec.x, y=rec.y-1, right=rec.right+1, bottom=rec.bottom+1, surface=[0x676904] }
  dx = 0x2EF(751) - rec.x ;  dy = 0x16(22) - (rec.y-1)
  → 0x4235E5(rect, ctrl=0x663410, index=1, dx, dy)          ← 5 参数
       → 0x47E0A0(rect, ctrl, index, dx, dy, flags=0x1008000, 0)   ← 7 参数
            · flags 0x1008000 = DDBLT_WAIT(0x1000000) | DDBLT_KEYSRC(0x8000)
            · 源面 = ctrl->[4] + index*0x1c + 0x18（表项里的 surface 指针）
            · 几何：W = rect.right-rect.left+1, H = rect.bottom-rect.top+1（记录盒尺寸）
                    0x47E050(ctrl, index, &a, &b) 取表项前两个 dword
                    0x47E4E0(rect, ctrl, &out, index, dx, dy) 做 dx/dy 裁剪
                    dst.left = rect.left + dx  **仅当 dx >= 0**（dx<0 时保持 rect.left 不动）
                    dst.top  = rect.top  + dy
                    再用 rect.bottom+1 夹住 dst 下边
            → 0x47E1B1 call dword ptr [ecx+0x14]   = IDirectDrawSurface::Blt ✓
              （返回码分支：0x80004005 / 0x80004001 / 0x80070057 / 0x8876006E 都走报错字符串 0x4ab9xx）
       → 0x4231DF(dst.left, dst.top, right, bottom)            ← 画边框（绿框）
```
**结论（已确证）**：可见按钮的位置与尺寸**都由记录盒 + 表项决定**，`dx/dy` 是叠加在上面的
「相对裁剪量」；记录盒同时充当**裁剪框**。这就是「改记录 → 画面被拉伸而不是平移」的结构原因：
把 `rec.x +224` 之后，`dx` 从 −11 变成 −235，裁剪/取源的计算整个跑到了另一个区段。

## 十一、同类老游戏宽屏补丁的通行做法（本轮 GitHub/网搜结论）

| 方案 | 代表 | 做法 | 对我们的意义 |
|---|---|---|---|
| **运行期 DLL 注入 + 代码 hook**（当前社区主流） | [alphayellow1/AlphaYellowWidescreenFixes](https://github.com/alphayellow1/AlphaYellowWidescreenFixes)（C++ DLL + Hook；工具链 Cheat Engine / x32dbg / Ghidra / HxD） | 不硬改常量，而是 hook 运行时函数：FOV 重算、HUD 元素按分辨率重排 | ⭐ 与我们同构：**hook `0x44ACDA`/布局初始化，在运行期改判定与坐标**，可绕开「静态常量被多处共用」的死结 |
| **显示层放大/兼容层** | cnc-ddraw、DDrawCompat、dgVoodoo2、DxWnd、Magpie | 只改呈现：整数缩放/保持宽高比/边框窗口；**DDrawCompat 明确声明「There is no API conversion involved」＝无放大能力** | 拿不到「一屏更多地图」，但零风险 |
| **源码级重制/移植** | DevilutionX(暗黑)、OpenRA(红警)、OpenXcom(X-COM)、**Open General/OpenGen 与 PG Forever（本仓两套主线！）** | 直接改 `SCREEN_W/H` + 布局代码 | 真正的答案，但＝换引擎（用户已排除） |
| **改 present Blt 让它整帧拉伸** | 本仓 `_ref\pg-cht` skill `retro-directdraw-hires-cjk` | 改 present 的 dst 尺寸 → DirectDraw 自动 StretchBlt（近邻，清晰但不增加内容） | 我们的目标是**反向**：不希望被拉伸 |
| **共享 dst/src RECT 陷阱** | 同上 skill | present 的 dst/src 若指向同一 RECT，改尺寸会变成越界取源 → 花屏/拉伸 | 与我们观察到的现象一致，需在 hook 里分离 rect |

**要点**：能拿到「真·更大视口」的社区案例，几乎都走 **DLL hook 重算** 或 **源码移植**；
纯静态改常量的成功案例集中在引擎布局较简单或社区投入数年的作品（C&C95 高分辨率补丁、SC1 宽屏等）。
