`EFILE_GUS` 共 7,173 个文件，真正含可见文本的只有三类：

### 层 1：`.xscn` 内的番号与地名

```
D:\OpenGeneral\EFILE_GUS\SCENARIO\*.xscn
文件 978 ｜ 槽位 69,732 ｜ 唯一串 32,914 ｜ 尾部残留 [(0, 978)]
```

| 类别 | 条数 | 占比 |
|---|---:|---:|
| 不含拉丁字母（纯数字/符号/编号） | 1,389 | 4.2% |

490 个文件 / 198,611 字符。与层 1 同源，**不需要独立翻译**，用层 1 同一张表逐行查即可。

| 目录 | 文件数 | 语言分布（实测） |

## 三、实测数据（不是推测）

### 3.1 网络可达性

| 目标 | 结果 |
|---|---|
| `translate.google.com` | **连接超时（不可用）**；同环境 `example.com` = 200 |
| `api.mymemory.translated.net` | **可用，免费，无需 key** |
| `cn.bing.com` / `fanyi.baidu.com` | 200 |
| `argosopentech` / `deepl` / `libretranslate` | 被拦 |
| PyPI / 清华镜像 | 200 ｜ `huggingface.co` **被拦** ｜ **`hf-mirror.com` = 200** |

### 3.2 机翻可用率实测（MyMemory，200 次请求）

| 语料 | 成功返回中文 | 结论 |
|---|---:|---|
| 100 段真实散文（英文层 3） | **94 / 100** | **草稿级可用** |
| 100 条高频 `.xscn` 串 | **10 / 100** | **不可用，且有害** |

`.xscn` 的失败不是「翻不出」，而是**翻错了更糟**：

```
12 ID            -> 12身份证件     ← ID 是「步兵师」，全错
3 PzArmee / 90 Leichte / 5 TA / 16 A / "Hermann Goring"  -> 原样返回
```

⇒ **机翻在层 1、层 2 上零价值。**

### 3.3 规则表覆盖率实测（`work\gus\rule_proto.py` + `rule_proto2.py`）

按「token 字典 + 序数/罗马数字规则」逐轮补字典，实测曲线：

| token 字典规模 | 完全覆盖 | 频次加权覆盖 |
|---:|---:|---:|
| 195 条 | 16.9% | 16.0% |
| **397 条** | **28.5%** | **25.2%** |

剩余 71.5% 的构成（**这是关键**）：

| 缺几个 token | 条数 | 占比 |
|---|---:|---:|
| 缺 0（已覆盖） | 8,763 | 28.5% |
| **缺 1 个** | **16,134** | **52.5%** |
| 缺 2 个 | 4,778 | 15.6% |
| 缺 3 个及以上 | 1,028 | 3.3% |

剩余未知 token 共 **17,969 个**，频次长尾：出现 ≥20 次的仅 94 个（占未知出现次数 7.6%）、≥5 次的 764 个（28.1%）。**绝大部分是只出现一两次的专名**（`Admiral Scheer` `Ariete` `Asashima` `Narew` `Totenkopf` `Wiking`…）。

⇒ **靠人工建 token 字典去啃长尾是错的方向**：要再补上万条一次性专名才能逼近全覆盖，成本远高于直接把整批丢给 LLM。

### 3.4 决定性成本数字

```
30,703 条待译串合计  384,356 字符 = 375 KB   （含重复计 62,282 次出现）
```

**全部 `.xscn` 待译文本只有 375 KB。** 按 4 字符/token 估：约 9.6 万 token 输入、7 万 token 输出——按主流 API 价格**不足 0.5 美元**。

散文层 954,045 字符 ≈ 24 万 token 输入、约 50–65 万 token 输出，**约 1–3 美元**。

**⇒ 阶段 4 全部的翻译 token 花费在 $1–4 量级。真正烧钱的是我的轮次与上下文，不是译文。**

## 四、四个方案（已按实测重排）

### 方案 A：纯 LLM 批量 —— **主力方案（推荐）**

**做法**：层 1 与层 3 都切批（每批 25–30 个文件 / 每批约 500 条串），每批一个子代理，**只做「读文件 → 写文件 → 回计数」**，原文不进主会话。层 2 用层 1 的同一张表查。

**证据**：层 1 全部文本 375 KB（< $0.5）、层 3 约 95 万字符（$1–3）。
**优点**：质量最好；无环境依赖；当天可开工；层 3 的专名歧义也能一并处理。
**缺点**：子代理可靠性在阶段 3 已被证伪（6/6 空手），必须**脚本化 + 我逐批复核**，不能放任。

### 方案 B：本地离线 NMT 初翻 + LLM 精修 —— **降级为层 3 备选**

**做法**：装 `torch`(CUDA) + `transformers` + `sentencepiece`（清华镜像），从 `hf-mirror.com` 拉英中模型跑在 4060 Ti 上，出初稿后由 LLM 精修。

**优点**：层 3 迭代时边际成本 0。
**缺点（实测后已明确）**：
- 对层 1 **无意义**——机翻在 `.xscn` 上实测 10% 成功且会输出 `ID`→「身份证件」这类错译；本地 NMT 属同类模型，同样不可用于番号。
- 对层 3 **省下的钱不足 3 美元**，却要付约 1 天搭环境的前置成本。
- 需先实测质量，不能预先承诺。

⇒ **仅在层 3 反复返工多轮、或对第三方服务稳定性有顾虑时才值得上。**

### 方案 C：免费网页机翻初翻 + LLM 精修 —— **层 3 备选**

**做法**：MyMemory 出初稿，LLM 精修。**优点**：无前置、实测散文 94% 成句。**缺点**：匿名配额限制，1,973 个文件跑起来慢且随时可能被掐；第三方服务可能消失。

### 方案 D：规则表 —— **不担任主力，改作「免费预处理 + 一致性校验器」**

**实测结论**：397 条 token 只覆盖 28.5%，长尾是 1.8 万个一次性专名，**人工建表的边际收益极低**。

**但仍值得保留，做两件事**（成本近零）：
1. **预处理**：把已覆盖的 8,763 条直接填好，只把剩余 21,940 条交给 LLM，减少约 29% 的请求量。
2. **一致性校验器**——这才是它最大的价值：LLM 翻完后，用规则表反查「同一 token 在不同串里是否译成了同一个词」（`InfDiv` 不能一处译「步兵师」另一处译「步师」）。**人工建立 18K 字典做不到全覆盖，但作为校验器只需要比对已知 token 的译法是否自洽**，可自动发现绝大多数不一致。

## 六、推荐组合（结论已按实测修正）

**主力：方案 A（纯 LLM 批量）+ 方案 D 作预处理与校验器。**

理由：
1. **阶段 4 的翻译花费本来就很小**（$1–4），把大量精力投在「省 token」上是捡芝麻——`.xscn` 全层 375 KB，本来就不贵。
2. **人工 token 字典无法覆盖 1.8 万个一次性专名**，方案 D 当主力在数学上就不成立（28.5% 就是它的天花板附近）。
3. 真正该省的是**轮次与上下文**：批量（25–30 文件/批）、原文不进主会话、子代理只回计数、每批即时复核。
4. 方案 B 留作层 3 的备选后手——**如果**层 3 需要反复返工多轮，再上本地 NMT。

**执行顺序（待批准）**：

1. **层 1**：规则表预处理（8,763 条免费）→ 剩余 21,940 条按 500 条/批交 LLM → 合并成 `xscn-map.tsv` → 规则表反查一致性 → 隔离目录试写 → `check_loop` 逐槽对拍。
2. **层 2**：用层 1 同一张表逐行查，落盘后用 `verify_all.py` 校验 `.xscn` ↔ `.txt` 硬桥。
3. **层 3**：按战役切批，每批 25–30 文件，子代理出稿，我逐批复核行数与换行。
4. 三项校验 + `check_loop` 异常 0 → `docs\81` 报告 → 用户实机 G4 验收。

| 风险 | 应对 |
|---|---|

| 网页机翻配额被掐 | 换端点或回退方案 A |
| 本地 NMT 质量不达标 | 该方案作废，不影响主力方案 A |
| 写坏原文 | 既有硬约束不变：**覆盖前独立命令备份**、写后回读、`check_loop` 逐槽对拍 |

## 八、验收判据（沿用 `docs\73` 的 G4 门）

2. 独立解析器零异常（`xscn.py verify` 结构偏差文件 0、尾部残留 0）。
