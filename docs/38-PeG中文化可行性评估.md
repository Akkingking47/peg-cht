## 一、结论摘要

**可行性判定：具备中文本地化基础，可行。属于「文本外置型」引擎，改造范围远小于 OpenPG。**

三条决定性有利证据：

1. **全部界面文本外置于纯文本文件**，且引擎有**官方多语言先例**——原版 PeG 1.0 就自带德语/法语文本包（`GUI97.DEU` / `GUI97.FRA`）。
2. **场景二进制文件不含任何文本**。213 个 `.scn` 每个只含 2 个文件名引用（`.map` / `.txt`），  
   46 个 `.map` 可打印串为 **0**。⇒ **不需要做 `.xscn` 那种二进制串区回写**（OpenPG 的最大工作量项在此直接消失）。
3. **源码是 1998 原版构建**（`PeG030.exe` TimeDateStamp `1998-08-24`，内含 `C:\modgen\main\Src\*.c` 调试路径），  
   文本统一走 GDI `DrawTextExA`，**全 exe 只有 1 处 `CreateFontA`**——字体问题只需改一个调用点的参数。

**改造范围概览**（明细见 §七）：

| 层          | 载体                                | 规模                             | 难度            |
| ---------- | --------------------------------- | ------------------------------ | ------------- |
| L1 界面字符串   | `Gui030.txt` / `Gui031.txt`       | 各 653 行 / 11.9 KB（**纯 ASCII**） | 低             |

## 三、界面文本渲染机制

### 3.1 渲染路径（反汇编实证）

全 exe 只有 **1 处** `CreateFontA` 调用（FO `0x70CFA` → VA `0x4718FA`），上下文为：

```
0x4718ac  mov  ecx, [0x676904]          ; DirectDrawSurface 对象
0x4718bb  call dword ptr [eax+0x44]     ; IDirectDrawSurface::GetDC   ← 取 GDI DC
0x4718c2  push 0x3c / lea ecx,[ebp-0x3c] / call memset   ; 清 LOGFONT
0x4718d2  mov  dword [ebp-0x3c], -12    ; lfHeight = -12  (12 像素字高)
0x4718eb  push 0x190                    ; FW_NORMAL
0x4718e9  push 0                        ; iCharSet = 0  = ANSI_CHARSET
0x4718dd  push 2                        ; iQuality = PROOF_QUALITY
0x4718db  push 2                        ; iPitchAndFamily = VARIABLE_PITCH|FF_DONTCARE
0x4718d9  push 0                        ; pszFaceName = NULL   ← 使用系统默认字体
0x4718fa  call dword ptr [0x6aa3ec]     ; CreateFontA
0x471918  call dword ptr [eax+0x68]     ; IDirectDrawSurface::ReleaseDC
```

**⇒ 全部游戏内文字 = `GetDC(表面)` → `CreateFontA` → `SelectObject`/`SetBkMode`/`SetTextColor` → `DrawTextExA` → `ReleaseDC`。**  
这是 90 年代「GDI 文字画到 DirectDraw 表面」的标准做法，**与字体文件无关，与图形引擎无关**。

### 3.2 文本 API 清单（GDI32 仅 7 个导入）

| DLL    | 文本相关导入                                                                                                                                                                                                   |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GDI32  | `CreateFontA` `SelectObject` `SetBkMode` `SetTextColor` `DeleteObject` `MoveToEx` `LineTo`                                                                                                               |
| USER32 | `DrawTextExA` `wsprintfA` `MessageBoxA` `DialogBoxParamA` `GetDlgItem` `GetDlgItemInt` `SetDlgItemInt` `SetDlgItemTextA` `SendDlgItemMessageA` `SendMessageA` `TranslateMessage` `TranslateAcceleratorA` |

⚠️ **关键**：**没有导入任何文本测量 API**（无 `TextOutA`、无 `GetTextExtentPoint32A`、无 `GetCharWidth*`）。  
⇒ 游戏**不计算文字宽度**，只在**固定矩形**里画字。这对本地化的含义见 §六.3。

### 3.3 文本来源分层

### 3.4 对话框（Win32 原生，非自绘）

## 四、字符编码

| 项            | 结论                              | 证据                                                                                                                                                         |
| ------------ | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 编码模型         | **单字节 8-bit ANSI**，无 Unicode 路径 | 全部文本 API 为 `...A` 变体（`DrawTextExA` / `CreateFontA` / `DialogBoxParamA` / `SetDlgItemTextA`）；**无 `TextOutW`/`DrawTextW`/`CreateWindowExW`**                 |
| 运行时码页        | 由**系统 ACP 决定**                  | 导入 `GetACP` / `GetOEMCP` / `GetCPInfo`；`IsValidCodePage`；`DrawTextExA` 按 CP_ACP 解释字节                                                                       |
| 无 UTF-8      | 是                               | 无 `MultiByteToWideChar(...CP_UTF8)` 用法、无 BOM 处理；全部文本文件实测**无 BOM**                                                                                          |
| DBCS 感知      | ⚠️ **未导入前导字节处理 API**            | 无 `IsDBCSLeadByte` / `CharNext` / `CharPrev` / `AnsiNext` ⇒ 引擎自身可能做**字节级**操作                                                                               |
| 源文本实际码页      | **cp1252（西欧）**，且高字节极稀少          | 根级 `*.TXT`：862,252 B 中高字节 **206 个（0.024%）**；`Scenario\*.TXT`：223,509 B 中 **94 个（0.042%）**；高频字节 `0x92`(’) `0xe4`(ä) `0xed`(í) `0xfc`(ü) `0xe9`(é) `0xf6`(ö) |
| `Gui030.txt` | **纯 ASCII（高字节 0 个）**            | 11,855 B 全为 ≤0x7F                                                                                                                                          |
| 行尾/终止        | **全部 CRLF，无 BOM，多数文件末行无换行**     | `Gui030.txt` 652×CRLF；`Name030.txt` 999×CRLF                                                                                                               |

**含义**：

- 出稿用 **GBK(936)** 即可，与 OpenPG 既有纪律（「GBK、无 BOM、换行沿用原文」）完全一致。
- ⭐ **「cp1252 假汉字」陷阱比 OpenPG 小一个数量级**：源文件高字节占比仅 0.02–0.04%（OpenPG 的 cp1252 残槽是成批的）。
- ⚠️ **风险点**：`DrawTextExA` 本身是 DBCS 正确的，但若引擎在别处用字节计数做**截断 / 定长字段 / 字符串比较**，一个 GBK 汉字被从中间切断就会出现「半个乱码字」。**这是必须实机验证的头号项**（详见 §六.2）。

## 五、字体对中文字符的兼容性

### 5.1 现状

- 游戏内文字：`CreateFontA(-12, 0,0,0, FW_NORMAL(400), 0,0,0, **ANSI_CHARSET(0)**, 0,0, PROOF_QUALITY(2), VARIABLE_PITCH|FF_DONTCARE(2), **pszFaceName = NULL**)`
- 对话框文字：`MS Sans Serif` 8pt（1 处 Arial，1 处 Small Fonts 7pt）

`pszFaceName = NULL` ⇒ GDI 返回**系统默认字体**（老系统上即 `System` 位图字体）。这解释了为什么安装包里**一个字体文件都没有**。

### 5.2 中文能否显示

| 环境                    | 预期                                                                                                                                                                               |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 简体中文 Windows（ACP=936） | ✅ **已离线实渲染验证通过（2026-10-10）**。`DrawTextExA` 按 CP936 解码 GBK 字节；GDI 选中的基础字体是 `Arial`（无 CJK 字形），但绘制时经**字体链接（font linking）**自动回退到系统中文字体 —— **实测成像正常，无豆腐块**。见 §5.3 |
| 英文/其他 Windows         | **不会显示**（ACP≠936，GBK 字节被当作 cp1252 显示为乱码）                                                                                                                                         |

### 5.3 ✅ 实测结论：**不需要字体补丁**（补丁参数留备）

**离线探针（2026-10-10，用 ctypes 复刻 exe 调用，未启动游戏）**：六方案实渲染 ——
详情 `peg\testbed\R1-font-probe-report.md`，证据图 `peg\testbed\out\R1-*.png`。

| 方案 | GDI 选中字面名 | 中文缺失字形 | 实渲染结果 |
|---|---|---|---|
| **exe 原参数**（face=NULL, ANSI_CHARSET） | `Arial` | 17/22（仅基础字体层面） | ✅ **中文正常显示**（链接回退） |
| 补丁：face=`SimSun`/`宋体`（charset 0 或 134 结果相同） | `宋体` | 0 | 中文正常，**但英文观感退化为宋体西文** |

⇒ **结论：保持原参数，不打补丁。** 原参数下英文为 Arial 平滑字形、中文由链接字体渲染，观感更好。
⚠️ **判据教训**：`GetGlyphIndicesW` 报字形缺失**不等于画不出来**（它只查基础字体的字形表），**必须实渲染看像素**。

**（备查）若将来在非中文系统运行或出现字体异常**，按下列单点补丁处理：

`CreateFontA` 在 exe 里**只有 1 个调用点**，因此：

> 把 VA `0x4718F9` 处的 `push 0`（即 `pszFaceName`）改为指向一段新字符串（如 `"SimSun"` 或 `"宋体"`），  
> 并把 `iCharSet`（VA `0x4718E9` 处 `push 0`）由 `0` 改为 **`134`（GB2312_CHARSET）**。

两处各改 1 个立即数即可覆盖**全部游戏内文字**。这与本工作区 OpenPG 的 L7/L1 经验（`docs\27`「字体必须 simhei.ttf」）同源，但**改的是 exe 的两个 push 常量，不依赖任何配置文件**。

> ⚠️ 顺序建议：**先实机验证「不改任何东西、直接写 GBK 会不会出字」**，再决定是否需要打补丁。

## 六、中文键盘输入

### 6.1 结论：**可以**，且几乎零成本

- 游戏内所有文本录入都在**标准 Win32 对话框**里，用**标准 `Edit` 控件**（74 个）。
- 导入 `TranslateMessage` + `DialogBoxParamA` + `SendDlgItemMessageA`/`GetDlgItemInt` ⇒ 走**系统对话框管理器**。
- **标准 EDIT 控件的 IME 由 Windows 自动处理**，游戏无需任何 IME 代码（也确实没有导入 `Imm*`）。
- ⚠️ 但需注意：现有 EDIT 多为**数字框**（如 `Enter number` / `Set Hex Data` / `Create Army` 的番号），  
  名字类字段（将领名、部队名、场景名）才是真正需要中文输入的入口。

### 6.2 未见**自绘**输入框

主地图画面无文本输入（由 `GetAsyncKeyState`/`PeekMessageA` 处理热键）。⇒ **不存在需要自己接 IME 的自绘输入场景**。

### 6.3 但存在「横向空间」问题（比输入更值得注意）

游戏**不导入任何文本测量 API**（§3.2），只在固定矩形里 `DrawTextExA`：

- 12px 字高下，一个汉字约 12 px 宽，一个拉丁字母约 6–7 px。
- ⇒ **同样字符数下，中文横向占位约为英文的 1.8 倍**；而矩形宽度固定 ⇒ **长译文会被裁切**。
- ⇒ **译文必须做字符数压缩**：**实测（2026-10-10）** 英文 5.7–6.0 px/字、中文 10.0–10.6 px/字
  ⇒ 同宽度下**中文可用字符数 ≈ 英文的 57%**；口径定为 **≤ 原文英文字符数的 55–60%**。  
  例：`Requisition Unit`(16) → 「购买单位」(4)；`Brilliant Victory`(17) → 「大胜」(2)。中文信息密度天然支持这一点。

### 6.4 已文档化的长度上限（官方 File Specs）

| 项                             | 上限                                       |
| ----------------------------- | ---------------------------------------- |
| 场景说明（`.txt`/`.ply`）显示         | **1,500 字符**（超出部分被忽略，与实际字体有关）            |
| `_M.TXT`（地图格名）/ `_U.TXT`（部队名） | 1,000 行                                  |
| `*.ply` 实际文件                  | **每个文件恰好 501 字节**（定长记录）⇒ 中文上限约 **250 字** |
| SCN 内文件名/索引字段                 | 20 字节（含 `.MAP` 等扩展名）                     |

### 6.5 ⭐ 实机实测（2026-10-10）：引擎**强制 `DT_WORDBREAK`** ⇒ 窄框中文会逐字折行

全部文字只有 **2 个 `DrawTextExA` 调用点**，均在文本 helper 内（反汇编实证）：

| VA | 内容 |
|---|---|
| `0x47170C` | 文本 helper 入口；**`0x4717E2  or al,0x10`** ⇒ 给每次绘制**强制或入 `DT_WORDBREAK(0x10)`**；`0x4717FD call DrawTextExA`（format ＝ 调用方 flags ｜ 0x10，rect 由调用方给） |
| `0x4701D1` | flags ＝ `0x410` ＝ `DT_CALCRECT ｜ DT_WORDBREAK`（**量高**用 —— 这就是它不需要 `GetTextExtentPoint32A` 的原因） |

**英文有空格 ⇒ 只在词间断行（单词再长也不折）；中文无空格 ⇒ GDI 可在任意字间断行。**
⇒ 矩形只要比整串窄，中文就**逐字折行**。

**离线复现**（`peg\testbed\wrap-experiment.py`，证据 `peg\testbed\out\wrap-experiment.png`）：
同字体、同 `DT_WORDBREAK`，把 `购买单位` 画进不同宽度矩形（高 14px ≈ 一行）：

| 矩形宽 | 画出 |
|---:|---|
| 16–20 px | `购`（每行 1 字） |
| 24–32 px | `购买`（每行 2 字） |
| 36–44 px | `购买单`（每行 3 字） |
| 48 px+ | `购买单位`（完整） |

### 6.6 ⭐⭐ 根因定案（治本）：行终止判定用「字符类别表」，而 0x80–0xFF 全被判为换行

**反汇编实证**（`Text.c` 的文本加载器 @VA `0x46E800`）：

```
0x46E810  call 0x46FB54                 ; 清空指针表
  逐文件（Equip30/gui030/misc030/name030/tips030）:
0x46E8CB  call 0x438769                 ; 读入整个 .txt -> 缓冲指针 + 总字节数
  逐【字节】扫描（[ebp-0x174] = 字节下标）:
0x46E962  ecx = byte; eax = <字符类别表指针>; cx = word [eax + ecx*2]
0x46E97B  and  ecx, 0x157               ; ← 只保留掩码内的类别位
0x46E987  cmp  [ebp-0x184], 0
0x46E98E  je   0x46E9E5                 ; ← 结果为 0 ⇒ 判定为【行尾】
0x46E9E5  if (行长 == 0) 跳过、【不占行号】  ; ⚠️ 空行不计数
0x46EA03  malloc(行长+1)                ; 每行独立分配（非定长，长度不限）
0x46EA1E  指针表[文件*0xFA0 + 行号*4 + 0x64C720] = 该行
```

**类别表**位于 VA **`0x4ABA8A`**（.data，256 × WORD；全局指针 `[0x4ABA80]` 指向它，`[0x4ABC8C]=1` 走内联分支）。实测：

| 字节 | class | `& 0x157` | 判定 |
|---|---|---:|---|
| `'A'` | 0x0081 | 0x0001 | 正常字符 |
| `'0'` | 0x0084 | 0x0004 | 正常字符 |
| `'.'` | 0x0010 | 0x0010 | 正常字符 |
| `' '` | 0x0048 | 0x0040 | 正常字符 |
| TAB/LF/VT/FF/CR | 0x0028 | **0** | **行尾（本意）** |
| 其它控制字符 | 0x0020 | **0** | 行尾 |
| **0x80 – 0xFF（全部 128 个）** | **0x0000** | **0** | **行尾 ❌** |

> **⇒ 任何 ≥0x80 的字节都被判为「行尾」，而 GBK 汉字的每个字节都 ≥0x80。**
> 于是写入中文后：**每行在第一个汉字的首字节处就被截断**，且「长度为 0 的行被跳过、不占行号」
> ⇒ **其后所有行号整体错位** ⇒ 按钮取到**别的行**的文案
> ⇒ 表现为「**英文选项对应位置漂移**」「**原来的英文选项也不对了**」「显示不全 / 方块」（错位 + 字节被切一半）。
> **三个症状 = 同一根因，且只在非 ASCII（中文）时触发。**

#### 治本补丁（已实现）

把表中 **0x80–0xFF 共 128 项由 `0x0000` 改为 `0x0040`**（MSVC `_BLANK`）：

- `0x0040 & 0x157 = 0x0040 ≠ 0` ⇒ 高位字节成为「普通字符」，**不再断行**；
- 选 `0x0040` 的理由：只置 `_BLANK` 位，**不置** `_UPPER/_LOWER/_DIGIT`，
  因此另外 25 处引用该表的代码对高位字节的 `isalpha/isdigit` 结果**仍为 false**；
- 该补丁**只影响 0x80–0xFF 这一片**，而原版数据是纯 ASCII（从不出现高位字节）
  ⇒ **对原版行为零影响**，风险极低。

**产物**：`PeG030zh.exe`（**原 `PeG030.exe` 零改动**，md5 `b00710ca…` 未变；补丁版 md5 `7aad9239…`）；
差异**恰好 128 个字节**，全部落在 `0xA938A..0xA9489` 且为偶偏移。
脚本：`peg/testbed/patch-lineterm.py`（`patch` / `verify` / `remove`）。

**影响面**：一次修好**全部 5 个文本文件**（`gui/equip/misc/name/tips` `.txt`）**＋ 场景 `.txt` / `.ply`**。

**机制**（`sub_46FEDD` @VA `0x46FEDD`）：

```
n = 该串在 rect 里需要几行  ← sub_471696 → sub_47010B → DrawTextExA(DT_CALCRECT|DT_WORDBREAK)
if (idx <= 0 || idx >= n) return str;     ; 装得下 ⇒ 原样返回
else  二分查找【字节偏移】mid ⇒ return str + mid   ; 装不下 ⇒ 从第 mid 个字节开始画
```

| | 换行 | n | 结果 |
|---|---|---:|---|
| 英文 | 只在空格断行 ⇒ 1 行 | 1 | `idx >= n` ⇒ **原样返回，永不错位** |
| 中文 | 任意字间断行 ⇒ 多行 | >1 | 走丢行分支，mid 是**字节**偏移 ⇒ **落在半个汉字上** ⇒ 掉字/串字/方块 |

⚠️ 量宽本身没问题：`sub_47010B` 出口（VA `0x4701F1` 起）确认 `*out1 = rect.right-left`（实测宽）、
`*out2 = 高+3`、返回 `= 高/14`（行数），全部 GDI 计算，**DBCS 正确**。问题只在「丢前 N 行」按字节做。

⇒ 无条件走「返回原串」⇒ **永不丢前 N 行**。同长度同位置，不破坏指令边界。
