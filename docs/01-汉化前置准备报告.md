## 三、关键技术机制（已从 exe 导入表与字符串证实）

### 3.1 文本编码链路 —— 中文可行的核心依据

`OpenGen.exe` 导入了以下 API：

```
MultiByteToWideChar     ← 单字节 → 宽字符
WideCharToMultiByte
GetACP / GetOEMCP / GetCPInfo   ← 取系统 ANSI 代码页
TTF_RenderUNICODE_Blended       ← 按 Unicode 字形渲染
TTF_RenderUNICODE_Solid
TTF_OpenFont / TTF_Init
```

即：**文本文件（单字节） → `MultiByteToWideChar(CP_ACP)` → UTF-16 → `TTF_RenderUNICODE` → FreeType 取字形**。

本机实测：

```
Active code page: 936
ANSICodePage = 936        (GBK / 简体中文)
```

> **推论：在中文 Windows 上，把中文按 GBK 编码写入文本文件，引擎会正确解码为 Unicode 并用 FreeType 渲染。**
> 这也解释了为什么现有 de/es/hu/pl 语言文件是单字节代码页（匈牙利语实测字节 `45 6C 73 F6 70 72 F5 ...` = CP1250/Latin-2 的 `Elsöprő győzelem`）而非 UTF-8。

**注意**：这是**依赖系统 ACP 的机制**。在非中文区域的 Windows（ACP≠936）上，GBK 中文会乱码。这是该方案的固有约束。

### 3.2 字体链路

exe 中检出的相关字符串：

```
FONTS\        C:\WINDOWS\FONTS\        %s\FONTS\%s        OpenFont.cfg
Font1=%s  Font2=%s  SzFont1=%d  SzFont2=%d      verdana.ttf / cour.ttf
```

- 字体搜索路径：**游戏根目录 `FONTS\`** → **`C:\WINDOWS\FONTS\`**
- 字体与字号通过 `Settings.cfg` 的 `Font1` / `Font2` / `SzFont1` / `SzFont2` 指定（当前 `verdana.ttf` / `cour.ttf` / 12 / 12）
- efile 目录下也可放 `OpenFont.cfg` 覆盖（参见 `OPENTXT_SAMPLE\OpenFont.cfg`，格式为 `字体文件, 字号`）
- **重要限制**：exe 只导入 `TTF_OpenFont`，**未导入 `TTF_OpenFontIndex`** → **不支持 `.ttc` 字体集合**。
  - 可用：`Deng.ttf`（等线）、`simhei.ttf`（黑体）、`simkai.ttf`、`simfang.ttf`、`NotoSansSC-VF.ttf`
  - **不可用**：`msyh.ttc`（微软雅黑）、`simsun.ttc`（宋体）

### 3.3 UI 字符串加载机制

exe 字符串：`Strings-??.txt`、`Default(English)`、`strings-`、`UI_Lang=%s`

- UI 翻译文件位置：**`OPENGUI\strings-<lang>.txt`**（`<lang>` 为 2 位 ISO 639-1 代码）
- 已有：`strings-de.txt` / `strings-es.txt` / `strings-hu.txt` / `strings-pl.txt`
- 语言选择存于 `Settings.cfg` 的 `UI_Lang=`（当前为空 = 默认英文）
- 文件在**启动时和每次载入游戏时**重新加载，改完重启或换局即可见效
- 模板：`OPENTXT_SAMPLE\strings-en-template.txt`（916 行）

### 3.4 efile 级本地化目录机制（重大效率优势）

exe 字符串：`TEXT-`、`STRINGS-`、`%s%s\`、`Could not open %s`

引擎支持把整个 efile 的文本资源按语言放进子目录，**运行期自动切换**，与原文完全分离：

```
EFILE_AG\
  ├─ equip.txt / nations.txt / fronts.txt / strings_efile.txt / SCENARIO\*.txt   ← 英文原文
  ├─ TEXT-DE\                                          ← 德语整目录
  │    ├─ equip.txt  fronts.txt  nations.txt  strings_efile.txt
  │    └─ SCENARIO\*.txt
  ├─ TEXT-ES\  TEXT-HU\  ...                            ← 其他语言
  └─ SCENARIO\
```

> **汉化只需新建 `TEXT-ZH\` 目录，不动任何原文。** 这是最干净、最易回滚的做法。

### 3.5 文本文件格式约定

- 行尾：**CRLF**（Windows）——`strings-*.txt`、`equip.txt` 实测均为 CRLF
- 编码：**无 BOM** 的单字节代码页
- `strings-XX.txt` 结构必须与模板**逐行对应**：模板明确警告 `Do not removed neither insert lines`。行错位会导致 UI 文本整体串位

## 五、前置准备清单

### A. 备份与安全（第一步，必做）

1. 备份即将改动的文本层（不必备份 1 GB 全部）：
   ```powershell
   # 示例：备份当前激活 efile 的文本
   Copy-Item D:\OpenPG2\Settings.cfg D:\DSH\军事游戏汉化\backup\Settings.cfg
   Copy-Item D:\OpenPG2\EFILE_AG D:\DSH\军事游戏汉化\backup\EFILE_AG -Recurse
   ```
2. **`Settings.cfg` 必须单独备份**——字体和语言开关都在这里
3. 记录原始状态：`EFolder=efile_ag\`、`Font1=verdana.ttf`、`SzFont1=12`、`UI_Lang=`（空）
4. 全程遵守「新建 `TEXT-ZH\` + `strings-zh.txt`」原则，**覆盖式修改原文视为违规操作**

### B. 字体（必做）

1. 从系统单体 TTF 中选用（**不能用 `.ttc`**）：
   - 首选 `C:\Windows\Fonts\Deng.ttf`（等线，微软为中文 UI 设计，简体全覆盖）
   - 备选 `simhei.ttf`（黑体）、`NotoSansSC-VF.ttf`
2. 复制到 `D:\OpenPG2\FONTS\`
3. 准备**冒烟测试用两套字号**：`12`（与英文一致）和 `14`（中文可读性更好），实测后定稿

### C. 文本工程（必做）

1. 建立三语对照参考：`strings-en-template.txt` + `strings-de.txt` / `strings-pl.txt`
   > 德语/波兰语译文可作为**军事与历史术语的参考**，避免二次造词不一致
2. 建立**术语表**（统一用词，最重要）：
   - 胜负等级：Brilliant Victory / Victory / Tactical Victory / Loss
   - 兵种：Infantry / Tank / Recon / Anti-tank / FlaK / Artillery / Fighter / Tactical Bomber / Level Bomber / Submarine / Destroyer / Battleship / Carrier / Cruiser
   - 目标类型：Soft / Hard / Air / Naval
   - 移动方式：Tracked / Half Tracked / Wheeled / Leg / Towed / Air / Naval / Amphibious
   - 地形：City / Airfield / Bocage / Escarpment / Fortification / Port / Stream / Swamp
   - 军衔与属性（Special attributes / Leaders）
3. 建立**行结构校验流程**（见 D-2），每次提交译文前必须跑

### D. 工具（必做）

1. **支持 GBK 的编辑器**：VS Code + `GBK`/`GB2312` 编码支持，或 Notepad++（可直接选 ANSI=GBK）
2. **校验/转换脚本**：本报告已附 `tools\txt-tool.ps1`
   - `-Action check`：检查编码、BOM、行尾、行结构与模板是否逐行对应
   - `-Action to-gbk`：UTF-8 工作稿 → GBK 出稿
   - `-Action to-utf8`：GBK 原文 → UTF-8 便于翻译/版本对比
   > 工作流建议：**以 UTF-8 保存工作稿**（便于 Git 版本管理），**发布前统一转 GBK**。
3. 版本管理：对 `TEXT-ZH\` 与 `strings-zh.txt` 建本地 Git 仓库，隔离于游戏目录

### E. 范围界定（需你决策，见第七节）

### F. 冒烟验证（POC）——**强烈建议在任何批量翻译之前完成**

一次性验证全部关键假设，成本约 20 分钟：

1. 复制模板 → `D:\OpenPG2\OPENGUI\strings-zh.txt`，转 GBK
2. **只翻译 15–20 个高频短词**（如 `Axis`→轴心国、`City`→城市、`Infantry`→步兵、`Brilliant Victory`→辉煌胜利）
3. 复制 `Deng.ttf` → `D:\OpenPG2\FONTS\`
4. 备份后改 `Settings.cfg`：`UI_Lang=zh`、`Font1=Deng.ttf`
5. 启动游戏，逐项确认：
   - [ ] 中文**能正常显示**（不是方块/乱码）
   - [ ] 语言下拉框是否出现 `zh` 选项
   - [ ] 12px 下中文**是否可读**
   - [ ] 14px 下**布局是否溢出**（按钮/表格列宽）
   - [ ] 译文较长时**是否被截断**
   - [ ] `equip.txt` 改名后单位名是否变化 → **判定 `equip.txt` 与 `equip.xeqp` 谁生效**

## 六、风险与待验证项

| ID | 风险 | 影响 | 对策 |
|---|---|---|---|
| R1 | **`equip.txt` 与二进制 `equip.xeqp` 谁被引擎读取** | 若是 `.xeqp`，则直接改 txt 无效，需用 `OpenSuite.exe` 重新编译 | POC 必测项 |
| R2 | **中文 12px 可读性差**（笔画糊连） | 需放大字号 | 实测；可仅放大 `Font1`（正文），`Font2`（表格）另议 |
| R3 | **放大字号导致固定布局溢出** | 按钮/表格/对话框文字被裁 | 逐屏实测；必要时缩短译文或改 UI 图 |
| R4 | **字符串 buffer 长度上限未知** | 超长译文被截断或溢出崩溃 | 先按「不超过原英文长度 1.5 倍」保守约束；实测边界 |
| R5 | **语言下拉框可能硬编码语言列表** | `zh` 不出现在选项里 | POC 验证；若失败可复用现有代码（如把 `strings-pl.txt` 内容替换为中文并沿用 `pl`） |
| R6 | **GBK 依赖系统 ACP=936** | 换到其他区域设置的机器会乱码 | 属固有约束，需在发布说明中注明 |
| R7 | **场景文本量巨大** | 全量 21 个 efile 不可行 | 必须聚焦单一 efile（见第七节） |
| R8 | **行错位** | `strings-xx.txt` 行数/结构与模板不一致会导致整个 UI 串位 | D-2 脚本强制校验 |

## 八、官网官方文档（补充侦察）

### 8.1 官方对语言文件机制的说明

**来源**：[Open General — Game Interface → Custom languages](https://www.luis-guzman.com/OpenGen_Interface.html)
（路径：open-general.com → Documentation → Overview，即 [OpenGeneral.html](https://www.luis-guzman.com/OpenGeneral.html) 的 User Interface 子页）

原文要点（意译，关键处保留原文）：

> Open General 界面**可以在不需要 Unicode 的前提下（as far as no Unicode is required）**翻译成不同语言。
> 语言机制**完全是可选的**，因为**所有字符串都已内置在可执行文件中，默认是英文**。
> 要启用额外语言，需要准备一个 `String-XX.txt` 文件（XX 为 ISO 639-1 代码），放到**主 OPENGUI 文件夹**。
> 当 Open General 发现一个或多个 `Strings-??.txt` 文件时，会向 **User Settings Dialog 中的语言下拉框**追加条目。**只有在下拉框中选定某种语言后**，所有字符串才会改为从该 `Strings-XX.txt` 读取。
> efile 文件夹也可以包含不同的 `Text-XX` 子目录……当选中 XX 语言时，OG 会**优先**从这些 `Text-XX` 子目录加载文本文件，**找不到的再回落到普通文件夹**。
> 安装包中已为 `EFILE_OLGWW2` 附带一个 `Text-ES` 子目录（含西语 DAK 战役场景文本）。
> **注：此功能目前正在审查中（This feature is currently under review）**。

### 8.2 由此得到的三条硬约束

1. **必须通过游戏内语言下拉框切换**。直接手写 `Settings.cfg` 的 `UI_Lang=zh` **不生效**——已实测：连官方语言 `de` 同样不生效（退出确认框仍显示英文）。
   正确位置：**User Settings Dialog（用户设置对话框）的语言下拉框**，需要进入游戏后操作。
2. **官方限定"以不需要 Unicode 为前提"** —— 这是对中文的**明确风险信号**。引擎面向 CP1252 / CP1250 这类单字节语言；中文是双字节字符集（GBK），引擎内部若存在按**字节**计算的逻辑（长度限制、截断、居中、换行），中文就可能错位。**必须实测。**
3. 官方标注该功能 **"currently under review"**（正在审查、可能变动），说明它不是稳定承诺。

### 8.3 官方文本文件规范（`Config files` 页）

[Config files](https://www.luis-guzman.com/OpenGen_ConfigFiles.html) 详述了 efile 级文本文件，**但全文未提及 UI 语言文件**：

| 文件 | 是否必须 | 说明 |
|---|---|---|
| `Nations.txt` | **不可省略** | 定义 efile 的国家；前两行为阵营标签（覆盖 `strings_efile.txt` 的 `[sides]`） |
| `Names.txt` | 可省略 | 前 31 行不用，此后每 31 行一组，按国家随机取指挥官名 |
| `TerrainEx.txt` | 可省略 | 地形行为参数；**不得增删行，只能改写数值** |
| `Strings_efile.txt` | 可省略 | efile 级字符串覆盖，段：`[Results] [Targets] [Spaces] [Movement] [Transports] [Classes] [Requisition] [Terrain] [UnitData] [Latitude]` 等 |
| `Colors.txt` / `Weather.txt` / `Fronts.txt` / `Eyear.txt` | 可省略 | 颜色 / 天气区 / 战线 / 基准年 |
| `Antique.ini` | — | 定义指挥官称谓的替代字符串（`EFILE_AG` 即用到） |
| `Pg1Mode.cfg` | — | PG1 兼容模式 |

另：官方明示 **所有文本文件行尾必须是 `[CR+LF]`**，与本地实测一致。

## 九、POC 实测结果（关键突破）

### 9.1 结论：中文汉化**实测可行**

| 假设 | 结果 | 证据 |
|---|---|---|
| H1 中文能正常渲染 | ✅ **通过** | 底部提示条显示「载入存档 \<Ctrl+L\>」，字形清晰、无乱码、无方块（`poc\zoom_bar.png`） |
| H2 引擎识别 `strings-zh.txt` | ✅ **通过** | 语言下拉框（User Settings → Select UI Language）出现 `zh` 条目 |
| H3 12px 中文可读性 | ✅ **通过** | `SzFont1=12` + `Deng.ttf`（等线）渲染清晰，**无需放大字号** |
| H4 14px 布局溢出 | ⏳ 未测 | 12px 已可读，非必须项 |
| H5 长译文截断 | ⏳ 未测 | 正式翻译时观察 |
| H6 `equip.txt` / `equip.xeqp` 谁生效 | ⏳ 未测 | 见 9.3 |

> 官方文档那句 **"as far as no Unicode is required"** 属于**保守/过时**的表述。
> 实测在本机（ACP=936）下中文完全可用：`GBK 文件 → MultiByteToWideChar(CP_ACP=936) → UTF-16 → TTF_RenderUNICODE → FreeType(Deng.ttf)` 这条链路成立。

### 9.2 【关键】语言开关的正确写法

**`UI_Lang` 存的不是语言代码，而是文件名基名（含 `strings-` 前缀）**：

| 写法 | 结果 |
|---|---|
| `UI_Lang=zh` | ❌ 无效，静默回退英文 |
| `UI_Lang=de` | ❌ 无效（官方德语也一样） |
| **`UI_Lang=strings-zh`** | ✅ **正确**，加载 `OPENGUI\strings-zh.txt` |

这一条让整个验证卡了很久：引擎匹配不上就**静默使用内置英文**（所有字符串都编译在 exe 中，这是默认行为，官方已说明）。

> **注意**：即使语言已正确切换，**"退出游戏"确认框等部分对话框仍显示内置英文** —— 印证了官方 "can be translated **up to a point**"（只能翻译到一定程度）。这类硬编码文本是汉化的**天然盲区**，需在交付说明中注明。

### 9.3 剩余待验证项

1. **`equip.txt` vs `equip.xeqp`（影响 OPENPG 单位名能否直接汉化）**
   `equip.xeqp` 是二进制编译产物（可打印 ASCII 仅 16.9%，无可读字符串），`equip.txt` 是明文源。
   探测方法：临时把 `equip.xeqp` 改名为 `equip.xeqp.probe-bak`，若单位名仍正常显示 ⇒ 引擎读 `.txt`（可直接汉化）；若单位列表缺失/报错 ⇒ 引擎读 `.xeqp`（需用 `OpenSuite.exe` 重新编译）。
   工具：`tools\build-poc.ps1 -Action probe-equip -EquipFile D:\OpenPG2\EFILE_OPENPG`
2. **长文本截断边界**：模板要求"尽量与原英文等长"，但德语译文普遍比英文长 50%+ 且工作正常，说明容忍度尚可；中文通常更短，风险低。
3. **`TEXT-ZH\` 目录机制**：需在 OPENPG efile 上验证 efile 级文本（`equip.txt` / `nations.txt` / `SCENARIO\*.txt`）的 `TEXT-ZH` 回退是否生效。
