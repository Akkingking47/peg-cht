## ⑥ R2/R3 实机反馈诊断 —— 根因定位：**引擎强制 `DT_WORDBREAK`**

用户跑完实机（4 张截图），反馈「文字漂移 + 英文对不上号」。

### 判读结论
- ✅ **正常**：底部状态栏 `Clear Roads`/`M2A3 Bradley`/`Ent:0`（来自 `MISC030.TXT`＋部队数据，本次未改）无漂移无乱码。
- ✅ **正常**：标题画面悬停标签 `档案`（2 字放得下，水平正确）。
- ❌ **异常**：地图画面悬停标签 `买单□` / `单□` —— 可见字 + **洋红方块**。

### ⭐ 根因（反汇编实证）
**全部文字只有 2 个 `DrawTextExA` 调用点**，均在文本 helper 内：
- helper `@VA 0x47170C`；**`0x4717E2  or al, 0x10`** ⇒ 给每次绘制**强制或入 `DT_WORDBREAK(0x10)`**；
  `0x4717FD call DrawTextExA`（format = 调用方 flags | 0x10，rect 由调用方给，helper 再叠加 dx/dy）。
- 另一处 `@VA 0x4701D1`，flags = `0x410` = `DT_CALCRECT|DT_WORDBREAK`（**量高**用，不是 `GetTextExtentPoint32A`）。

**英文有空格 ⇒ 只在词间断行；中文无空格 ⇒ GDI 可在任意字间断行** ⇒ 矩形窄就逐字折行。

### ⭐ 离线复现（`peg\testbed\wrap-experiment.py`，证据 `out\wrap-experiment.png`）
同参数下把 `购买单位` 画进不同宽度矩形（高 14px ≈ 一行）：
`16–20px→购` · `24–32px→购买` · `36–44px→购买单` · `48+→购买单位`。
**矩形只够一行时，第二行只露出上半截 ⇒ 12px 汉字的上半截看起来就是一个方块**
⇒ 截图里的「洋红方块」是**折行后第二行首字的残影**，不是缺字、不是乱码。

### 硬规则（新增，写进 docs\38）
> **按钮/短标签可用宽度仅 2–3 个汉字**，超出的字折到第二行、因矩形只留一行而**看不见**（只剩残影）。
> ⇒ 看起来像「贴错标签」（用户说的「对不上号」），实为**译文比格子宽**。

## ⑨ ⭐⭐ 治本成功：根因定案 + 补丁已产出（用户选「按治本来」并提供关键线索）

### ⭐ 根因（反汇编实证，`Text.c` 加载器 @VA `0x46E800`）

```
0x46E8CB  call 0x438769        ; 整个 .txt 读入内存 -> 缓冲指针 + 总字节数
0x46E962  cx = word [<类别表> + byte*2]
0x46E97B  and ecx, 0x157       ; 只保留掩码内的类别位
0x46E98E  je  0x46E9E5         ; ==0 ⇒ 【行尾】
0x46E9E5  行长==0 ⇒ 跳过、【不占行号】      ; ⚠️ 空行不计数
0x46EA03  malloc(行长+1)        ; ⚠️ 每行独立分配 —— 非定长，行长度本来不受限
0x46EA1E  指针表[文件*0xFA0 + 行号*4 + 0x64C720] = 该行
```

**字符类别表 @VA `0x4ABA8A`**（.data，256×WORD；全局 `[0x4ABA80]` 指向它，`[0x4ABC8C]=1` ⇒ 走内联分支）。实测：

| 字节 | class | & 0x157 |
|---|---|---|
| `'A'` 0x81 · `'0'` 0x84 · `'.'` 0x10 · `' '` 0x48 | | ≠0（正常字符） |
| TAB/LF/VT/FF/CR = 0x28；其它控制 = 0x20 | | **0（行尾，本意）** |
| **0x80 – 0xFF（128 个）** | **0x0000** | **0 ⇒ 也被当成行尾 ❌** |

**⇒ 任何 ≥0x80 的字节被判为行尾，而 GBK 汉字每字节都 ≥0x80**
⇒ 中文行**在第一个汉字的首字节处就断**，产生的 0 长度行**不占行号** ⇒ **其后行号整体错位**
⇒ 按钮取到**别的行**的文案 ⇒ 用户三个症状（**英文选项对应位置漂移 / 原来的英文也不对了 / 显示不全+方块**）**同一根因**，且**只在中文触发**。

### ✅ 补丁（治本，已产出并校验）

把表中 `0x80–0xFF` 共 128 项 **`0x0000` → `0x0040`**（MSVC `_BLANK`；`0x40 & 0x157 = 0x40 ≠ 0` ⇒ 不再断行）。

- 校验：差异**恰好 128 个偶偏移字节**，全部落在 `0xA938A..0xA9489` ✅。

## ⑪ 查证：Hard/Soft Attack 有无标准军语

**结论：分两层，答案不同。**

| 层面 | 军语 | 依据 |
|---|---|---|
| `Hard Target` / `Soft Target` | ✅ **有（国军标正式术语）** | **GJB 1365-92《核火力运用的术语与符号》**：硬目标＝「具有较强抗力，不易摧毁的目标」；软目标＝「具有较小抗力，易于摧毁的目标」；亦见《核打击目标》（按抗超压能力分类） |
| `Hard Attack` / `Soft Attack` | ❌ **没有** | 兵棋**机制词**（攻击某类目标的强度值），英文侧也是游戏造词，真实条令无此术语 |

⇒ **军语化的正确做法**＝军语词根＋机制后缀：**`硬目标攻击` / `软目标攻击`**。
⭐ 佐证：工作区总库中 **`EFILE_NASHORNPBEM` 已 LOCKED 过该译法**（`Hard Attack→硬目标攻击`、`Hard target→硬目标`，HIGH 置信）。

⚠️ **语义偏差**：军语「硬目标」偏重**抗毁能力**（加固机堡/地下设施/装甲工事），
而 PeG 的 hard target **特指装甲单位** ⇒ 军语「硬目标」⊃ 游戏 hard target（借用，范围略宽）。

**三条路线**：A `硬目标攻击/软目标攻击`（军语最正＋与前作 LOCKED 一致，但需同步改行71/72）·
B `对装甲攻击/对人员攻击`（**当前采用**，最好懂但军语性弱）· C HOI4 `对装甲杀伤/对人员杀伤`。

**产出**：`peg/research/术语平衡口径.md` 新增「Hard/Soft Attack 军语查证」小节（含对照表）。**译文未改，待用户决策。**

## 第 31 轮 ★★★ 日期汉化·真因 ＝ 游戏调用 Windows `GetDateFormatA`

**用户**：第 30 轮（改 exe 内建 CRT `lc_time` 月份/星期表）**仍然无效**。

### 排查过程（关键：先证伪自己上一轮的假设）
1. 发现目录有 **9 个 exe**；确认 `PeG030.exe` 是运行的（`tasklist`）。
2. 查进程启动时间 **17:02:58** > 补丁时间 17:01:58 ⇒ **进程确实加载了打过补丁的 exe**
   ⇒ 说明**引擎根本没读那张表**，不是「没重启」。
3. 复查补丁后 exe：英文月份/星期名**一个不剩**（仅剩缩写表 `May`）⇒ 补丁本身没问题。
4. 转查**导入表**：发现 `0x08AAA0 "LC_TIME"` 与 **`GetDateFormatA` / `GetLocaleInfoA/W` / `GetUserDefaultLCID`**
   —— 日期是由 **Windows 区域 API** 生成的。

### 真因（反汇编 `GetDateFormatA` 唯一调用点，文件偏移 0x7BE7F）
```
0x7BE75  push 0x96             ; cchDate=150
0x7BE7A  push 0x65A3A0         ; lpDateStr
0x7BE7F  push 0               ; lpFormat=NULL（系统长日期格式）
0x7BE81  push &SYSTEMTIME      ; 自 .SCN 起止日期（year+2000 @0x67E6AC / month @AA / day @A8）
0x7BE85  push 2               ; dwFlags=DATE_LONGDATE  ★
0x7BE86  mov eax,[0x499148]    ; ★ LCID 取自全局「语言」变量
0x7BE8B  push eax
0x7BE8C  call [0x6AA460]      ; = GetDateFormatA
```
- 全局 `0x499148`（.data，文件 0x96948）**初值 9 = LANG_ENGLISH**；
  语言分支写 **7 = LANG_GERMAN / 12 = LANG_FRENCH**（见 0x4273A、0x42778 及 0x708E0 的 `.deu`/`french` 分支）。
- ⇒ `GetDateFormatA(9, DATE_LONGDATE, 2006-4-3, …)` = **"Monday, April 3, 2006"**，与截图一致。
- **教训**：第 30 轮看到 exe 里有月份字符串就认定是数据源 ⇒ 错。**应先查导入表确认「是谁在格式化日期」。**

### 修复（`work/peg/patch-date-lcid-zh.py`）
`0x7BE86`：`A1 48 91 49 00`(`mov eax,[0x499148]`) → **`B8 04 08 00 00`(`mov eax,0x0804`)**（等长 5 字节）
- **ctypes 实测**：`GetDateFormatA(0x0409,…)`→`Monday, April 3, 2006`；
  **`GetDateFormatA(0x0804,…)`→`2006年4月3日`** ✅（`0x0404`zh-TW 会出 Big5 乱码，故必须用 `0x0804`）
- exe md5：`88afab90…` → **`c462e897…`**；备份 `peg\testbed\PeG030.exe.pre-lcid-zh`

**备份链（勿删）**：`PeG030.exe.orig-backup`（原版）→ `…pre-month-zh`（MBCS后）→ `…pre-lcid-zh`（月份补丁后）

**备注**：第 30 轮的 `lc_time` 补丁**保留**（无害；万一有 CRT 路径仍能用上），但它**不是生效的那一刀**。

### 第 31 轮续 · 用户确认日期汉化成功 ✅
用户：「牛逼没错了，显示中文了」。`patch-date-lcid-zh.py`（`0x7BE86` 强制 LCID=0x0804）**生效**。
