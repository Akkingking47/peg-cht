## ★ 重大突破：数据层中文乱码彻底解决（manifest activeCodePage=UTF-8）

### 问题
UTF-16 数据文件（`equipment.pgeqp` / `*.pgscn` / `pg.pgcam`）里的中文在游戏内显示为乱码
（如"1941 西线" → "1941 η↓"，1:1 错字映射），而 UI 层 htm 的中文完全正常。

### 根因（静态分析 exe 得到）
- exe 导入了 `MultiByteToWideChar` / `WideCharToMultiByte` / `GetACP`
- HTMLayout 接口导入的是 **`HTMLayoutSetElementHtml`（窄字符版，按 UTF-8 解析）**
  与 `HTMLayoutSetElementInnerText16`（宽字符版）
- 引擎读入数据文件得到宽字符，再经 `WideCharToMultiByte(CP_ACP=936/GBK)` 转成窄字节
  交给 HTMLayout → **HTMLayout 按 UTF-8 解析 GBK 字节 → 乱码**

### 解法（不需要改 exe 逻辑，零风险）
让**该进程**的 CP_ACP 变成 65001(UTF-8)：给 exe 的**嵌入 manifest**追加
`<activeCodePage>UTF-8</activeCodePage>`。

- **外部 `PGForever.exe.manifest` 无效**：exe 已有内嵌 RT_MANIFEST(24)，系统会忽略外部文件
- 嵌入 manifest 位置：文件偏移 `0xAC27C`，资源数据区 **Size=346**（CodePage=1252）
- 原 manifest 含缩进+换行共 346 字节；压成单行并**去掉 trustInfo**（仅声明 asInvoker，是默认行为）
  后为 246 字节 ⇒ **等长就地替换**，其余 100 字节补空格
- **文件大小与资源结构零改动**，脚本：`tools/patch_manifest.py`
- 效果：`1939 / 德国在欧洲发动一连串闪电战攻势，自波兰开始。`
  `1941 西线 / 为攫取中东的石油，轴心国挥师横扫北欧。` 等全部正常显示 ✅
- 只影响这一个进程，不动系统设置、不影响其他程序

### 顺带解决的环境难题
- **截图必须用 `PrintWindow`**（`tools/pwshot.py`），不能用屏幕 BitBlt：
  桌面浏览器会遮挡游戏窗口，导致截到浏览器或空白
- 窗口原生固定 **500×600 @ (710,220)**，SetWindowPos 改尺寸会被游戏改回
- 鼠标合成点击**不稳定**（有 4~7px 坐标偏差，且焦点易被抢），键盘偶尔有效
- 结论：能用「启动+PrintWindow 截图」验证的，就不要依赖点击

## ★★ 第二个根因：UTF-8 缓冲区按"字符数"分配（P2 exe 补丁）

### 症状
manifest 补丁后中文能显示，但仍有损坏：
- 主菜单战役列表**最后一条**必坏：`1943 东线` → `1943 东缃`，描述位置露出 `body>`（HTML 标签泄漏）
- 战役简报长文本被截断
- **htm 界面的中文完全正常**

### 关键判据：htm 正常 vs 数据文件损坏
`*.htm` 由 HTMLayout 直接读 UTF-8（不经 exe 转换）→ 正常；
`pgcam/pgscn/pgbrf` 经 exe 转 UTF-16 再转 UTF-8 → 损坏。**问题在 exe 的转换调用。**

### 定位（反汇编 WideCharToMultiByte，15 个调用点）
唯一命中 `sar reg,1 + push 同reg` 模式的是 VA `0x46D64A`（文件偏移 `0x6CA4A`）：
```asm
sar   eax,1      ; eax = (end-start)/2 = 宽字符数 N
push  eax        ; cbMultiByte = N        ← 元凶
push  65001      ; CP_UTF8
call  [WideCharToMultiByte]
```
`cbMultiByte` 收到**字符数 N**，但 UTF-8 汉字占 **3 字节** → 只有 1/3 空间 → 截断并越界读相邻内存
（相邻内存是 HTML 模板，于是 `</body>` 被当正文显示出 `body>`）。

### 解法（1 字节等长替换）
`0x6CA3E: D1 F8 (sar eax,1 → N)` → `D1 E0 (shl eax,1 → 4N)`
`4N ≥ 3N` 够用；文件大小恒定。**脚本 `tools/patch_w2m_buffer.py`**

### 残余
VA `0x473347` 附近有第二个同类调用点，`cbMultiByte` 与 `cchWideChar` 复用同一 `[ebp+0x10]`，
等长替换会让源长度越界读，需 code cave，**暂留未改**。

## ★★★ 最终定位并修复：中文长文本截断真因（P4）——推翻 P2

### 现象
战役列表 5 条：前 3 条正常，**第 4 条描述变 `伯body>`，第 5 条整条消失**。
超长中文（95 字/UTF-8 249 字节）压力测试：只显示 3 条，第 3 条从中间截断。
英文原版完全正常。

### 完整加载路径（已梳理）
```
pg.pgcam (UTF-16LE)
 → 0x4517E0 战役列表生成：sprintf(0x48DA60模板) → std::wstring::append(0x413EB0)
 → 0x4014C0 按元素 id 遍历设置（HTMLayoutVisitElements, id="ScnList"）
 → 回调 0x4031B0 → vtable 0x482104[0]
 → 0x401680 ★
      push 3 (CP_UTF8)
      call 0x402B50        ; W2U8：宽字符 HTML → 局部 std::string 的 UTF-8 字节流
      mov edx,[esi+4]      ; 源宽串对象
      mov eax,[edx-0xC]    ; ★BUG：取「源宽串字符数」当 htmlLength
      mov ecx,[esp+4]      ; 局部 UTF-8 串数据指针
      call HTMLayoutSetElementHtml(hElem, utf8bytes, eax, 0)
```
简报路径 `*.pgbrf` → `briefing.htm` + id `BrfText` → `0x4475C0` → **`0x4476A0 call 0x4014C0`** → 同一函数，同样受益。

### 根因
**长度与数据来源错配**：
- 内容 = `0x402B50` 转出的 **UTF-8 字节流**（汉字 3 字节/字符）
- 长度 = **源宽串的字符数**（`[源串-0xC]`）
- 官方签名 `HTMLayoutSetElementHtml(HELEMENT, LPCSTR html /*utf8bytes*/, UINT htmlLength, UINT where)` 要求**字节数**

→ HTMLayout 只解析前 N 字节 → 标签不闭合 → 条目渲染失败；后续条目偏移错位整条丢失；
HTMLayout 回落默认模板 `<html><body...>&nbsp;</body></html>` → 屏幕泄漏 `body>`。
**英文无碍**（ASCII 下字节数==字符数）。截断比例随中英混合比浮动（观测 ~2/3）。

内存物证：`poc/len_probe/seg_*.bin` 中 HTML 完整正确，该段 **292 字节 / 188 字符**（比值 1.55）。

### 修复（P4，6 字节等长 NOP）
`0x402B50`（W2U8）**返回时 eax 恰为 WideCharToMultiByte 的返回值 = 实际写入的 UTF-8 字节数**
（函数尾部只改 ebx）→ 把中间两条无用/错误指令 NOP 即可：

| 项 | 值 |
|---|---|
| VA | `0x4016A0` |
| 文件偏移 | `0xAA0` |
| 原 | `8B 56 04 8B 42 F4`（mov edx,[esi+4] / mov eax,[edx-0xC]）|
| 新 | `90 90 90 90 90 90` |
| 大小 | 753664 不变 |

`0x4016A6` 起本来就用 `[esp+4]` 作 utf8bytes，与 eax 恰好配对。
脚本：**`tools/patch_exe_all.py apply-p4 | revert-p4 | status`**

### 验证（对照实验，同一份超长中文）

|---|---|
| 未打补丁 | 只显示 **3 条**，第 3 条中间截断 |

常规数据：未修 → 3 正常 + 第4条`伯body>` + 第5条消失；**已修 → 5 条全正常**。
截图：`poc/cam_shot_{before,after_fix3,final,stress_orig,stress_patched}.png`

### 全调用点审计（`tools/audit_sethtml.py`）
11 处 `SetElementHtml` + 11 处 `SetElementInnerText16`：
**只有 `0x4016B6`（即 0x401680 内）内容来自 W2U8** → 只有这一处错配，已修。

4. **「同一画面半中半英」= 两个不同来源**，是最好的定位线索。

## ★★ Close 一词两义「按文件整表覆盖」方案失败 → 改为「短语规则」（重要教训）

但 **`unit.htm` 里同时存在两种 Close**：

- 第 271 行 `<div ...>Close</div>`                          ← **菜单按钮，要「关闭」**

⇒ 按钮被译成了「抵近」。**`per_file` 粒度不够（文件级 < 需要语境级）。**

**正解：用「含标记的短语规则」精确锁定元素内部文字**

```json
"global": {

  ">Close</span>": ">抵近</span>",          // ★ 限定在 span 内 → 属性面板

  "Close Defense:": "抵近防御:",            // ★ unit.htm 的尾词
  ">Close<": ">关闭<"                       // 菜单按钮
}
```

- `replace_all` 原来对**所有** en 都加 `(?<![A-Za-z])...(?![A-Za-z])` 词边界，
  会让含 `<` `>` 的短语规则失效 → 改为**仅纯字母词加边界，含标记的短语直接字面替换**。
- `build_rules` 过滤 `_` 开头的注释键。

## ★★★ 第三轮：「Close防御 + 目标类型英文 + 左右栏不对齐」——真凶是**替换时误伤 HTML 属性**

```python
TAG = re.compile(r'<[^>]*>')

        return '\x01%d\x02' % (len(store) - 1)
```

### ★ .pgcam 战役 —— 本轮最重要的结构发现
`.pgcam` 是按位置解析的定位格式，**只有 3 类文本会显示给玩家**：
1. `# Entry points` 段数据行 col 0（入口名）+ col 2（简介）
2. `# Outcomes` 段每行 col 0（结算名）

**绝不能译**（实证）：
- `# Entry points` col 1（`Label in campaign path`）—— 恒等于 `# Campaign path` col 0
- `# Scenarios` 段 col 0（Label）—— 与 Campaign path col 0 同一键空间
- `# Campaign path` 整段 12 列（Label / *.pgbrf 文件名 / NextLabel / Prestige）
- 佐证：exe 命令协议串 `outcome %s for scenario %s`、`campaign path label %s` 证明这些词是**匹配键**

⇒ 初版提取脚本把 `scn_label`（1413 条）当可译项是**严重误判**，修正后从 463 条收敛到 **102 条**。
**若误译会直接破坏战役树**，务必牢记。

`AXIS VICTORY`/`ALLIED VICTORY` 在 exe 内是 `.pgscn` 写回模板 → `.pgcam` 侧可译，`.pgscn` 侧不动。

1. **尾随空格**：部分原文带尾随空格（`'US M18 '`），生成器必须保留首尾空白，
