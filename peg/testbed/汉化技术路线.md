# PeG 汉化技术路线（社区范式对照 + 本作落地）

> 2026-10-10 调研。**结论：不改成「双字节引擎」，任何中文尝试都会不断出现新毛病**
> （行号错位 / 掉字 / 方块 / 标签偏移 全会轮流出现）。下面是社区通行做法与本作的逐一对应。

---

## 一、调研到的三条权威范式

| 来源 | 核心内容 |
|---|---|
| **《游戏汉化中的双字节问题处理原理》**(CSDN) | 引擎若按**单字节**循环取字，必须在取字处加 `test al,80h` 判断；遇中文前导字节要**多取一字节**拼成一个「字符」再交给贴字函数 |
| **RealLive 引擎汉化笔记**(CSDN) | ① `iCharSet` 改为 **134 (GB2312_CHARSET)**；② 引擎里对前导字节的判定常硬编码成 `cmp al,0A0h`（日文习惯），GBK 是 `0x81–0xFE` ⇒ **判定范围必须扩大**；③ 还要处理 `MultiByteToWideChar` 的代码页解析 |
| **CK2DLL / rUGP-Fuck**(GitHub/DeepWiki) | 现代做法：**DLL 注入 + Hook**，不改原 exe，运行时替换「字符边界判定」；模式匹配扫描内存里的 `cmp al,XXh` 特征串 |
| 微软 **Q75439 / DBCS-Enabled Programs** | DBCS 下**不能用 `++`/`--` 走字符串**，也不能 `string[i]` 随机访问；要用 `CharNext/CharPrev/IsDBCSLeadByte`。lead byte 范围表：**CP936 GBK = `0xA1–0xFE`（trial `0xA1–0xFE`；实际 GBK lead `0x81–0xFE`）** |

**三条范式指向同一件事：把引擎从「单字节」改成「双字节感知」。**

## 二、本作（PeG030.exe）的实际情况

### 2.1 关键发现：`[0x4ABA80]` 不是「行尾表」，是 C 运行库的 `_pctype`

反汇编 CRT 的 `_isctype`（`sub_4802D0`）：

```
0x480308  test byte [esi + edx*2 + 1], 0x80   ; 取 _pctype[hi] 的高字节测 bit7
                                              ;  = 测 _pctype[hi] & 0x8000 == _LEADBYTE
0x4802E8  mov ax, word [edx + ecx*2]          ; 同一个表 [0x4ABA80]
```

⇒ 表 @VA **`0x4ABA8A`** 就是 `_pctype`（256 × WORD 字符类型表），
`0x8000` 位 = **「这是双字节前导字节」**（`_LEADBYTE`）。

**原版表的致命缺陷**：`0x80–0xFF` 共 128 项全是 `0x0000`
⇒ **前导字节标志从未设置** ⇒ 引擎与 CRT 里所有双字节判定（**20 处 `_isctype` 调用**）全部「不认中文」。

### 2.2 另一个开关：`__mbcodepage`

`[0x4ABC8C]` = CRT 全局 `__mbcodepage`，原版 = **1**。
引擎里有 **20 处** 都是这个模式：

```
cmp dword [0x4ABC8C], 1
jle <走内联 ASCII 表>          ; ← 原版走这条
    <走 _isctype() 双字节路径>  ; ← 只有 __mbcodepage > 1 才走
```

⇒ **引擎本身有双字节路径，只是从没被启用。**

### 2.3 exe 的能力清单（证明它「本来就能显示中文」）

| 能力 | 状态 |
|---|---|
| `MultiByteToWideChar` / `WideCharToMultiByte` / `GetCPInfo` / `GetStringTypeA` / `LCMapStringA` / `CompareStringA` / `GetLocaleInfoA` | ✅ 全部导入（KERNEL32） |
| `IsDBCSLeadByte` / `CharNextA` | ❌ 未导入 ⇒ 引擎不靠 API 判前导字节，靠 **`_pctype` 的 `0x8000` 位** |

## 三、本作落地的三项改动（`patch-mbcs.py`）

| # | 内容 | 位置 | 原 → 新 |
|---|---|---|---|
| ① | 字体字符集 | `0x4718E3`（CreateFontA 的 iCharSet 压栈） | `6A 00` → **`6A 86`**（134 GB2312_CHARSET） |
| ② | `_pctype` 标出前导字节 | `0x4ABA8A + 0x81..0xFE` | `0x0000` → **`0x8040`**（`_BLANK｜_LEADBYTE`）；`0x80`/`0xFF` → `0x0040`；**`0x00–0x7F` 一个字都不动** |
| ③ | 启用 MBCS | `[0x4ABC8C]` | `1` → **`936`** |

**为什么安全（对原版英文零影响）**
1. 英文文本是纯 ASCII（实测 `Gui030.txt` 无任何 ≥0x80 字节）⇒ ②③ 的判定路径永不触发；
2. `_pctype[0x00–0x7F]` 保持原值 ⇒ `isalpha/isdigit/isspace` 等分类结果不变；
3. 离线模拟验证：用新表解析原版 `Gui030.txt` → **仍是 653 行，逐行内容完全一致** ✅

### ⚠️ 一次险些酿祸的错（已修正）
第一版脚本把整张 `_pctype` 刷成了 `0x0040`，**毁掉了 ASCII 的分类位**
（`_pctype['A']` 从 `0x0081` 变成 `0x0040`）⇒ 词法判定会全废。已改为**只动 `0x80–0xFF`**，
并在 `verify` 里加了 ASCII 抽查断言（`0x41 → 0x0081`、`0x20 → 0x0048`）防再犯。

## 四、与前三轮已修的两处合起来看

| 轮次 | 发现的「单字节假设」 | 修法 |
|---|---|---|
| 第 2 轮 | 加载器逐字节扫描 + `(class & 0x157)==0` 判行尾，`0x80–0xFF` 全判为行尾 ⇒ 行号整体错位（**＝「英文按钮标注偏移」**） | 表格改造（现并入 ②） |
| 第 3 轮 | `sub_46FEDD` 按**字节**二分查找丢前 N 行 | 曾试「关掉该分支」⇒ **实测会改变英文标签显示，已撤回** |
| **第 4 轮（本轮）** | **`_pctype` 未标前导字节 + MBCS 未启用** ⇒ 引擎全部双字节逻辑停摆 | **三项标准改动** |

## 五、如果这轮仍不彻底：下一步是 DLL 外挂（CK2DLL 路线）

不改 exe、可随时卸载，用被导入的 DLL 做代理（本作已导入 `WINMM.dll`，
但目录里 `ddraw.dll` 已被 Svens Wrapper 占用 ⇒ 用 `winmm.dll` 或 `version.dll`），
在里面 Hook：

- `MultiByteToWideChar` / `GetStringTypeA` —— 强制按 CP936 解析
- `DrawTextExA` —— 替换字符边界判定（rUGP-Fuck 的 `AttachCharacterPatch` 模式）
- `CreateFontA` —— 强制 GB2312 字符集 + 明确字面名

**这条路不用动原 exe 一个字节，风险最低，是社区现在的主流做法。**
