## 三、需订正的表述（2 处）

### 3.1 「保持原结构 / 等长」表述不准确 —— 文件实际全部变短

文档多处表述为数据文件"保持原有结构与 TAB 分隔"，容易被读作长度不变。**实测全部变短**：

| 文件 | 原长度 | 现长度 | 变化 |
|---|---|---|---|
| `equipment.pgeqp` | 84790 | 83554 | **−1236** |
| `pg.pgcam` | 18668 | 17192 | **−1476** |
| `*.pgscn` ×38 | 502928 | 498894 | **−4034**（38/38 全部缩短） |
| `*.pgbrf` ×178 | 50687 | 35886 | **−14801**（173 缩短 / 3 变长 / 2 等长） |

**这本身不是缺陷**：这些都是**行式文本格式**（`# 注释` + `键\t值` 或 `<p>` 片段），
没有内部长度头或偏移表，引擎按行/按 `\t` 解析。已用两项独立证据确认安全：

1. pgscn **行数逐文件完全一致**（38/38）
2. pgscn **结构行（数字、键名）异常数 = 0**，变化只发生在译文行

> 3 个"变长"的 pgbrf（`0158`/`0159`/`0176`）原内容为 `<p> </p>`（8 字节，纯空白），
> 译文 `<p> </p>\r\n`（10 字节）仅多一个换行，无影响。

**建议**：文档改为「保持**行结构**不变；因中文与英文字节长度不同，**文件总长度会变化**，已通过行数一致性校验」。

### 3.2 `*.pgbrf` 的编码写错了

- **POC 报告写**：`pgbrf` 为 UTF-16LE+TAB
- **实测**：`*.pgbrf` 是 **UTF-8（无 BOM）**，文件头直接是 `b'<p>Your first mi'`
- 对照组：`pgeqp` / `pgscn` / `pgcam` **确为** UTF-16LE + BOM（文件头 `FF FE`）

| 文件类型 | 真实编码 |
|---|---|
| `equipment.pgeqp` | UTF-16LE + BOM |
| `*.pgscn` | UTF-16LE + BOM |
| `pg.pgcam` | UTF-16LE + BOM |
| **`*.pgbrf`** | **UTF-8（无 BOM）** |

**好消息**：`tools/deploy_pg_brf.py` 与 `brf_check.py` 的实现是**按 UTF-8 处理的**——即
**代码是对的，只有文档描述写错了**。部署产物用 UTF-8 解码可读、内容正确，进一步证明实现无误。

## 六、复核方法说明（可复用）

本次核验采用的可复用判据：

1. **资源结构安全性**：解析 PE，确认 `RT_MANIFEST` 的 Size 未变（346）
   → 证明"等长替换未破坏资源树"，比单纯看文件大小更严格
2. **补丁精确性**：与原版逐字节 diff，确认改动范围
   → 证明没有误伤其他代码
3. **文案写入正确性**：对每条译文在 exe 中 `find()`，并校验**偏移未漂移**
4. **文本文件改动安全性**：对行式文本，核验**行数一致** + **结构行（非字母行）零差异**
   → 比"长度不变"更适配文本格式
5. **回滚完整性**：以「含中文 ⇔ 已改动」为判据全库扫描
   → 找出"改过但无备份"的文件，若为零则备份完整
