## 三、根因

`0x401680` 里存在**长度与数据来源错配**：

* **内容**：`0x402B50` 转换出来的 **UTF-8 字节流**（汉字 3 字节/字符）
* **长度**：取自 **源宽字符串的字符数**（`[源串-0xC]`）

`HTMLayoutSetElementHtml` 的 `htmlLength` 要求 **UTF-8 字节数**（官方头文件：`LPCSTR html /*utf8bytes*/, UINT htmlLength`）。

于是 HTMLayout 只解析前 N 个字节（N = 字符数），**远小于真实字节数** → 标签未闭合 → 该条目渲染失败；后面的条目因累计偏移错位而整条丢失，HTMLayout 回落默认模板 `<html><body...>&nbsp;</body></html>`，于是屏幕上泄漏出 `body>` 片段。

**为什么英文没问题**：ASCII 下字节数 == 字符数，完全一致。
**为什么表现为"约 2/3 截断"**：中文 3 字节 + ASCII 1 字节混合，比例随内容浮动。

### 内存物证

运行时 dump 出的 HTML **在内存里是完整正确的**（`poc/len_probe/seg_*.bin`）：

```
<option value=4><div.caption>1943 西线</div><div.details>主力已投入东线，轴心国必须守住欧洲柔软的下腹部。</div></option>
<option value=5><div.caption>1943 东线</div><div.details>面对战线过长的苏军，轴心国试图在东线重夺主动权。</div></option>
```

该段 HTML：**292 字节 / 188 字符**（比值 1.55）→ 用 188 当长度，只能解析到 UTF-8 流的前 64%。

## 四、修复

### 原理

`0x402B50`（W2U8 封装）**返回时 `eax` 恰为 `WideCharToMultiByte` 的返回值 = 实际写入的 UTF-8 字节数**（其函数尾部只改 `ebx`，未动 `eax`）。

因此把中间两条「无用 + 错误」的指令直接 NOP 掉即可：

```asm
; 0x4016A0  原（6 字节）
8B 56 04        mov edx, [esi+4]      ; 取源宽串（下面要用字符数 → 错）
8B 42 F4        mov eax, [edx-0xC]    ; ★ 字符数，错

; 0x4016A0  新（6 字节）
90 90 90 90 90 90                     ; NOP，保留 0x402B50 返回的 eax（UTF-8 字节数）
```

`0x4016A6` 起原本就用 `[esp+4]`（局部 UTF-8 串）作 `utf8bytes`，**与 eax 恰好配对**。

### 补丁位置

| 项 | 值 |
|---|---|
| VA | `0x4016A0` |
| 文件偏移 | `0xAA0` |
| 原字节 | `8B 56 04 8B 42 F4` |
| 新字节 | `90 90 90 90 90 90` |
| 文件大小 | 753664 字节（**不变**） |

脚本：`tools/patch_exe_all.py apply-p4` / `revert-p4` / `status`

## 七、⚠️ 重要更正：P2 补丁方向错误

此前的 P2 补丁改的是 **`0x6CA3E`（`sar eax,1` → `shl eax,1`）**，位于 **`fwrite` 内部**（`0x46D05C`）的 W2M 转换中。

**该点与屏幕显示完全无关** —— 它只影响写文件的长度计算。

这就是 P2 施加后中文截断问题依旧的原因。

**处理建议**：P2 若已施加，建议回退（或至少不要把它当成中文显示的修复）。当前 exe 仍含 P2。是否需要回退需评估其对「导出/存档」功能的影响后决定。
