# 标准译名库 · 分层架构提案（通用 + 系列 + 专项并行）

> 2026-10-12。起因：用户指出「总词库现在是不是变成**专项词库**了？我期望**专项和通用并行**，
> 例如游戏选项是系列化专项化的，地名/人名/部队名/军事用语适合做成通用」。
> 本文件是**数据实测 + 架构提案**（尚未改动主库结构）。

## 一、现状问题（实测）

主库 `standard-glossary.tsv`：**23,476 行**，唯一维度是 `scope`（6 个值）：
`EFILE_OLGWW2 17,863 · EFILE_OPENPG 3,445 · EFILE_NASHORNPBEM 1,892 · PEGWW2_UI 213 · PEGWW2_DOCS 42 · PEGWW2_EQP 21`

**问题**：`scope` 全是"项目/efile"维度 ⇒ 库事实上成了**若干专项库并排**，
**通用知识被按 scope 重复存储，且没有任何机制表达"这条是通用的"**：

| 症状 | 实测 |
|---|---|
| 通用知识重复存放 | 唯一原文 21,549 条里，只有 1,125 条出现在 ≥2 个 scope；其余**每个项目自己存一份**，新项目要从零再译或再抄 |
| 跨项目漂移**无人管** | 冲突清单只按 `(en, scope)` 算 ⇒ **同一条目跨 scope 打架完全隐身**。放开算立刻抓到 **6 条真漂移**（下表） |
| 无法只对"通用层"施加统一约束 | 想规定"地名全工作区统一"，现在没有落点 |
| 无法只对"专项层"放开 | 游戏选项/菜单各项目本就该不同，却和地名混在同一平面 |
| 缺"系列层"⇒ 同类问题反复出现 | 本次"前作 PeG 层未同步"那 4 条（`Profile`/`Sharpshooter`/`Set Prestige`/`Prestige Allocated Per Turn`），正是**缺系列层**的症状 |

**跨项目漂移实测（6 条）**：

| 原文 | 分歧 | 类别 |
|---|---|---|
| `Bone` | 博讷(OLGWW2) ｜ 博纳(OPENPG) | 地名 |
| `Brunn` | 布伦(OLGWW2) ｜ 布吕恩(OPENPG) | 地名 |
| `Gace` | 加采(NASHORNPBEM) ｜ 加塞(OPENPG) | 地名 |
| `Lukov` | 卢科夫(NASHORNPBEM) ｜ 卢库夫(OLGWW2) | 人名 |
| `Serafimov` | 塞拉菲莫夫(NASHORNPBEM) ｜ 谢拉菲莫夫(OLGWW2) | 人名（Се- 的两种通行转写） |
| `SNOW` | 雪(OLGWW2) ｜ 雪地(OPENPG) | 天气标签（应为专项） |

## 三、⭐ 建议架构：**三层并行 + 显式覆盖**

```
glossary/
  common-glossary.tsv    通用层  ~18k   地名·人名·国名·史实部队名·装备名与型号·军语·数值·兵种·编制·地形天气·缩写
  series-glossary.tsv    系列层  ~200   PG/PeG/PG2 家族共享的机制词（VH=胜利格·威望·BV/V/TV/Loss·部署与补给·装备特性名）
  scope-glossary.tsv     专项层  ~5k    各项目自定：保留原文政策·菜单/面板文案·战斗提示·指挥官技能·架空专名·长文本
  override.tsv           覆盖登记 ——   专项(或系列)覆盖上层的**显式声明**（原文｜层｜覆盖为｜理由）
  standard-glossary.tsv  合并视图（**现有工具照常用**；新增 `layer`/`over` 两列，不改前 8 列顺序）
  common-drift.tsv       ⭐ 新增：**跨项目漂移清单**（现有工具完全没有这一层检查）
```

### 四条规则

1. **通用层：一条原文只允许一种中文**。出现分歧 ⇒ 进 `common-drift.tsv` 等人工裁定
   （现在这类漂移**完全没人管**）。
2. **系列层**：给同引擎/同游戏家族共享。本 session 那 4 条「前作未同步」正是缺这一层的症状 ——
   有了系列层,"前作/本作同一条机制词"就有了共同的落点。
3. **专项层可覆盖上层，但必须显式登记**（`override.tsv` 带理由）：
   校验时 **未登记的偏离 = 错误**，已登记 = 提示。这样"故意不同"与"不小心不同"被区分开。
4. **查询/校验按三层合并解析**（`专项 > 系列 > 通用`）；`scope` 列保留，但不再当唯一维度。

### 与现状的兼容

- `standard-glossary.tsv` **仍是合并视图** ⇒ `glossary.py` / `check_glossary.py` 继续可用（只多两列）。
- 三层拆分由生成器自动产出；`scope` 维度不丢（专项层内部仍按 scope 记）。
- 迁移**机械可完成 ~95%**（上面三条判据），剩 **202 条 `TERM` 需人工二分**
  （可先按关键词自动分类，再逐条确认）。

## 四、收益

| 收益 | 说明 |
|---|---|
| 新项目**只写专项层** | 通用层直接继承（不必重译 7,000 个地名），起步成本大幅下降 |
| 通用层**能强制收敛** | 地名/人名/部队名跨项目一致；漂移在**入库时**就被拦（本次 6 条） |
| 系列层**解决同引擎同步** | 不再需要"人工记住前作怎么译"（本次 4 条前作未同步） |
| 检查**按层分语义** | 通用层冲突＝真问题；专项层分歧＝正常设计。误报大幅下降 |
| 与"专项和通用并行"的期望一致 | 通用层回答"这个地名全工作区怎么译"，专项层回答"这个游戏的这个按钮怎么叫" |

## 六、参照项目 `wicanr2/pg-cht`（裝甲元帥/太平洋元帥 繁中化）的借鉴

> 2026-10-12 实读其仓库（本地副本 `_ref/pg-cht`）。它做的是 **PG/AG/PacGen 三部曲**汉化，
> 与我们在同一条路上，且**已经把我们缺的几件事做了**。

### 6.1 它的架构（可对照）

| 它的做法 | 落在哪 |
|---|---|
| **词库＝唯一真相 + 可重生**：「改譯名就改這裡」；`apply_translations.py` 用**原檔 + glossary** 重生成品；**repo 不存成品与游戏本体** | `pg2/翻譯/README.md` + `apply_translations.py` |
| **按用途分层**成 6 份小词库 | `glossary.tsv`(UI/軍語/國名，带 `檔類` 列) · `glossary_equip.tsv`(装备 740) · **`glossary_short.tsv`(槽位受限短名 24)** · `briefings_glossary.tsv`(散文 384) · `NAMES-姓名庫.tsv`(人名 402，标 `音譯/史實`) · `戰役.tsv`(战役元数据 55) |
| **通用与专项并存的文件布局** | `pacgen/docs/knowledge-base/`：`equipment-crossgame-consistency.md`（**跨作品收敛**）＋ 每个作品一份 `equipment-{panzer,allied,pacific}-general.md`（专项） |
| **替换策略**：整行命中→替换；整行分词且**全部命中**→拼接；否则**保留原文**；**明确不做子串替换**（防误伤型号） | `apply_glossary.py` |
| **对齐来源与进度记账** | 「對齊三部曲 93、自譯 268、**待查 27**」「對齊百科 66、WebSearch 查證 94、自譯 352、**待複核 341**、船艦/番號照抄 13」 |
| **长度预算程控** | `bytes` 列（Big5 实测，非手算）＋ `build_size_report.py`；结论「最長 18B，全部 ≤20B」 |
| **跨作品错误分级** | 152 笔不一致 → **纯风格差 125 / 用词不当 20 / 實質錯誤 27**；表内 `[錯誤]` 标注 + 优先修 27 笔 |

### 6.2 直接吸收（4 条修正）

1. **加一层 `short`（槽位受限短名）**：他们为字节槽位单独做一层（`AA→防`、`Carrier→航母`、`Italy→義`、`Apr→四`，备注 `縮字 2B（原 2B slot）`）。
   ⇒ 我们加 `short` 层，并把**显示宽度/字节**做成库的一列（我们的 UI 实测 ≤5 汉字、状态栏窄位）。
2. **`common-drift` 照他们的报告形态做**：**分级**（實質錯誤/用词不当/纯风格差）＋建议统一名＋长度＋**优先级**（先修實質錯誤）＋决策留痕。
   ⇒ 比我原来只列"漂移"更完整。
3. **加"待定"状态并计数**：他们用 `待查`/`待複核` 显式记未完成态；我们的库只有 LOCKED/POLICY，未定的只能塞例外表。
4. **成品可重生 + 版本戳**：词库为唯一生成源（我们抄 `apply_glossary` 的替换策略），成品**可随时从"原件＋词库"重生**，并戳词库 hash。

### 6.3 我们更强、要守住（3 条）

| 项 | 它的问题 | 我们的优势 |
|---|---|---|
| **项目维度** | 词库只有 `檔類`（文件类），**没有 scope/项目维度** ⇒ 同一英文在不同作品的差异只能靠"跨作品报告"人工收敛 | 我们已有 `scope` + 三层继承 + `override.tsv` 显式覆盖 |
| **脚本可重跑** | `build_glossary.py`、`extract_undone_lines.py` **硬编码 `/tmp/claude-…/scratchpad/` 路径** ⇒ 不可重跑，**与它自己的"可重生"原则矛盾** | 我们刚因"源没钉原件"吃了大亏（40 份回流污染）⇒ 源钉原件＋防呆闸必须守住 |
| **口径** | 涵蓋率按**唯一字串**算 ✅ 更合理 | 我们实测层表本就按键去重（23,378 行/23,350 唯一串），引用率两口径都是 **15%** ⇒ 之前"16%"的结论站得住 |

### 6.4 结论

它印证了方向（**通用＋专项并行、词库为源、可重生、跨作品收敛报告**），
并补上我们缺的三件东西：**短名层 · 长度预算 · 漂移报告的分级形态**；
而我们设计的 **scope × 三层继承 × 显式覆盖 × 可重跑闸门**，正好补它的短板。
⇒ **两者结合**才是完整的：`层(通用/系列/专项) × scope(项目) × 檔類(用途) × 槽位(长短)` 四维。
